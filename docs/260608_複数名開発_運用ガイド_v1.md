# 複数名・複数AIでの共同開発 運用ガイド v1

対象: ID社の開発関係者（北川さん・開発メンバー）＋ AI（Cowork / Claude Code）。
目的: 同じプロジェクト（branding.bz）を複数の人・複数のAIセッションで同時に進めるとき、進捗・実装・要件を破綻なく共有する。
位置づけ: 本ガイドは「今日（2026-06-08）実際にやった進め方」を雛形として体系化したもの。各ルールに実例を添える。

---

## 1. 役割分担（人とAIの分業）

| 主体 | 担当 | やらないこと |
|------|------|--------------|
| 北川さん（オーナー） | 方向性・要件の判断、設計の承認、破壊操作/pushの承認 | 細かい実装作業（AIに委譲） |
| Cowork（設計・検証担当のAI） | 調査、設計書、指示書の作成、DBの独立検証、判断材料の提示 | 本体コードの実装・コミット |
| Claude Code（実装担当のAI） | コード実装、マイグレーション適用、コミット、push、デプロイ | 設計の独断決定、未承認のpush/DROP |
| 並行セッション | 限定タスク（例: 別機能のWIP） | 同じファイル/マイグレへの同時着手 |

原則: **設計と実装を別主体に分け、検証も実装者とは別主体が行う**（今日はCoworkがDBをSQLで独立突合）。一人/一AIが「設計→実装→自己検証」を完結させない。

## 2. 進捗の共有: 3つのファイル

フォルダ直下に常設し、誰（人・AI）が来ても現在地が分かる状態にする。

- **`{コード}-PROJECT-STATUS.md`**: 現在地・完了事項・決定ログ。「何が終わり、何が次か、なぜそう決めたか」を時系列で残す。例: 今日の「負債是正 順序1→5→6」「Step 0→0.5→1a」の進行。
- **`TASKS.md`**: タスク一覧（未着手/進行中/完了）。承認待ち・ブロック中も明記。
- **指示書フォルダ（フォルダ直下に集約）**: 後述の指示書を `日付_テーマ_指示書_v1.md` で蓄積。「次に何をやるか」が物として見える。

## 3. 指示書の規約（実装の受け渡し単位）

実装はすべて「指示書」を介して渡す。口頭の曖昧な依頼にしない。

**命名**: `YYMMDD_テーマ_指示書_v1.md`（プロジェクトのファイル命名規約に準拠。日付先頭・アンダースコア区切り・`_v1`連番）。
**構成（今日の雛形）**:
1. 背景・目的
2. 方針（承認済みの判断を明記）
3. 手順（SQL・編集対象・順序）
4. 検証（独立に確認できる項目）
5. 禁止事項（やってはいけないこと）

**承認ゲート**: 破壊的操作（DROP・削除・本番push）は指示書内で必ず「停止して承認を得る」段に分ける。今日は「調査→報告→承認→実行」の2フェーズを徹底（負債調査、WIP整理、slogan/mvv、Step 1a すべて）。

## 4. 要件・設計の共有

- **設計書（`YYMMDD_◯◯設計_v1.md`）**: 実装前に論点と選択肢を文書化し、判断点を列挙して承認を得る。例: 今日の「Step1スキーマ設計」（関係の持ち方3案、第一カットのスコープ）。
- **決定ログ（採用表など）**: 「なぜこの案を採ったか」を残す。例: 「ブランドオントロジー ノード採用表」。後から来た人が議論を再現できる。
- **`CLAUDE.md`（恒久ルール）**: プロジェクト固有の不変ルールを集約。AIは毎セッション読む。例: 今日追記した「マイグレはローカル.sql先行」。要件が変わったらここを直す。

## 5. git運用（複数セッション・複数人で壊さない）

今日いちばん事故が起きやすかった領域。ルール化する。

- **部分コミット**: 自分のタスクのファイルだけを `git add`（または `git commit -- <path>`）。`git add -A` で他者のWIPを巻き込まない。今日は色改修や別機能WIPが混在する中、hunk単位で抽出して混入ゼロを維持。
- **非fast-forward時はforce pushしない**: 並行セッションがmainを進めていたら `stash → rebase → push → stash pop` で統合（今日Step 4で実施）。`--force` 禁止。
- **WIPの退避**: 進行中の別機能は `wip/機能名` ブランチへ退避し、mainの作業ツリーをクリーンに保つ（今日のlearning-structure）。
- **stashは勝手にdropしない**: 中身不明のstashは保持。破棄は承認後。
- **同じファイル/マイグレに2セッションで同時着手しない**: 重複・コンフリクトの元。オーナーを1つに決める（今日のphilosophy materializeは並行を破棄し単一オーナー化）。

## 6. DB・マイグレーションの規律

- **ローカル.sql先行**: マイグレは必ず `supabase/migrations/<version>.sql` を先に作ってから適用。リモート直適用でローカル未記録にしない（今日2度乖離が発生→恒久ルール化）。
- **破壊操作の前にバックアップ**: DROP前に退避テーブルやコメントへ全行記録（今日のbrand_guidelines理念4列・companies各列）。
- **dual-run**: jsonb→正規化のような移行は「新を作る→両方並行→読み替え→表示パリティ確認→旧を消す」の順。読むコードが本番に残る間は消さない（portal/valuesの教訓）。
- **参照のrepoint漏れに注意**: 列/テーブルを消す前に、表示だけでなくAI/分析の読み手も全部grepして向き先を変える（slogan repointの教訓）。

## 7. 検証の文化

- **独立検証**: 実装者の報告を、別主体がSQL/grepで突き合わせて裏取り（今日はCoworkが毎回DBを独立確認）。
- **表示パリティ**: 移行では「移行前後で表示が一致」を最重要項目に。
- **段階チェック**: 大きな変更は段ごとに `build`／advisors／パリティを確認し、段ごとに承認コミット。

## 8. AIへの依頼の型（再利用テンプレ）

1. オーナーがCoworkに目的を伝える
2. Coworkが調査し、判断点を提示（AskUserで選択）
3. 合意後、Coworkが指示書を作成
4. オーナーがClaude Codeに「この指示書を実行して」と渡す
5. Claude Codeが実装・検証・報告（破壊操作は停止して承認待ち）
6. Coworkが独立検証 → 次の指示書へ

---

## 付録: 今日のセッションが踏んだ「協働の落とし穴」と対処
- 複数セッションのWIPが作業ツリーに混在 → 部分コミット＋WIP退避で回避
- マイグレがリモートにだけ存在しリポジトリ未記録（2回） → ローカル.sql先行ルール
- pushが非fast-forward（並行作業先行） → rebase統合・force禁止
- 本番バグが未コミットWIPに埋もれていた（/portal/values） → WIP整理で発見・修正
- 同一作業を2セッションが重複着手しかけた（philosophy materialize） → 単一オーナー化

このガイド自体も `CLAUDE.md` から参照し、運用が変わったら更新する。
