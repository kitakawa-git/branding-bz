# ブランドオントロジー C案 詳細設計書 v1

**作成日:** 2026-07-18
**位置づけ:** 未来設計レビュー v2 で合意した方針（C案＝初期実装 / B案＝将来の正規モデル）の詳細設計。コード変更は行わない。設計確定のためのスペック。
**反映した精緻化（v2フィードバック）:**
1. 進捗は**重み付き**。`desired_evidence` に `importance_weight` / `achievement_rule` / `verification_method` / `target_value` / `target_unit`。表示名は「**理想像の実証進捗**（証拠獲得進捗）」。"ブランド何％完成"の断定は避ける。
2. Desired Evidence の状態を**2軸**に分離：実行状態（planned/in_progress/paused/cancelled・手動）と達成状態（unmet/partially_met/met・**原則動的判定**、手動は例外レビュー）。
3. `realizes` → **`verifies`**（実績は「達成を立証する」役割）。
4. **Vision ≠ Desired Brand State**。初期は vision をアンカーに `requires` で運用するが、「Vision＝理想のブランド像」とは定義しない。将来 `desired_brand_states` を独立追加できる構造を維持。Value Proposition は **target / transition_candidate / current / retired**、達成しても自動昇格せず**管理者レビューで current 昇格**。

## 3. relation_type 確定案

既存6種（`guides`/`evidencedBy`/`promisedTo`/`communicatedAs`/`constrainedBy`/`conflictsWith`）は不変。**C案で追加する4種：**

| relation_type | 起点(kind) → 対象(kind) | 自然文 | 時制/性質 |
|---|---|---|---|
| `aspiresTo` | value_proposition〈target〉 / philosophy → philosophy(vision) | 「A は B（理想）を目指す」 | 未来・任意（理想への接続を明示したい時） |
| `requires` | philosophy(vision) → desired_evidence | 「理想 A の実現には B が必要」 | 未来 |
| `toBeEvidencedBy` | value_proposition〈target〉 → desired_evidence | 「未来の約束 A は B で裏づけられる予定」 | 未来 |
| `verifies` | proof_point → desired_evidence | 「実績 A は、獲得目標 B が達成されたことを立証する」 | 達成時＝現在 |

### 3-1. `realizes` vs `verifies` vs `satisfies` vs `fulfills`（最終提案）

| 候補 | 含意 | 評価 |
|---|---|---|
| `realizes` | 実績がDEを"実現する" | DEを抽象目標として"実体化"のニュアンス。**部分達成や複数実績の合算と相性が悪い**。却下 |
| `fulfills` | "満たし切る" | 完了前提。partially_met を表せない。却下 |
| `satisfies` | 要件を"満たす" | 妥当（要件工学の語彙）。複数で積み上げOK。次点 |
| **`verifies`（採用）** | 達成を"立証する" | **`verification_method` カラムと語が一致**。「実績は達成を確認/立証する」＝事実が達成状態を裏づける、という因果が正確。partially_met とも整合（複数の verifies が閾値に積み上がる） |

**最終提案：`verifies`。** 自然文「実績Aは、獲得目標Bが達成されたことを立証する」。`verification_method`（検証方法）と対で、"どう確かめるか"→"確かめた事実" が一本の線になる。
※既存 `evidencedBy`（提供価値→実績）との向きの違いは意味の違い（VPは実績に"裏づけられる"／実績はDEの達成を"立証する"）なので許容。

## 4. 状態遷移図

### 4-1. Desired Evidence：実行状態（手動）

```
        ┌─────────┐  着手   ┌──────────────┐
  作成→ │ planned │ ─────→ │ in_progress  │
        └─────────┘        └──────────────┘
             │                 ↑     │
             │ 中止        再開 │     │ 一時停止
             ▼                 │     ▼
        ┌───────────┐      ┌────────┐
        │ cancelled │      │ paused │
        └───────────┘      └────────┘
   （cancelled は進捗の分母から除外。paused は現達成度を保持）
```

### 4-2. Desired Evidence：達成状態（原則・動的判定）

```
  verifies 実績 × achievement_rule で自動判定
  ┌───────┐  一部の実績  ┌────────────────┐  条件充足  ┌─────┐
  │ unmet │ ──────────→ │ partially_met  │ ───────→ │ met │
  └───────┘             └────────────────┘          └─────┘
        ↑___________________________________________|
                実績の取消・条件見直しで再計算（後戻り可）
  ※ achievement_state_override があるときのみ手動値を優先（レビュー記録必須）
```

### 4-3. Value Proposition：ライフサイクル（昇格は管理者レビュー）

```
  ┌────────┐        ┌──────────────────────┐  管理者レビュー  ┌─────────┐
  │ target │ ─────→ │ transition_candidate │ ─────────────→ │ current │
  └────────┘  DEが  └──────────────────────┘   （明示昇格）   └─────────┘
      │      met到達         │                                    │
      │                      │ 却下（まだ恒常提供でない）           │ 提供終了
      ▼                      ▼                                    ▼
  ┌─────────┐          （target へ戻す）                     ┌─────────┐
  │ retired │ ←──────────────────────────────────────────── │ retired │
  └─────────┘
  ★ DEが met でも自動で current にしない。transition_candidate で"昇格待ち"にし、
    管理者が「恒常的に提供可能」と判断してレビュー昇格。単発実績≠恒常価値。
```

## 5. 整合性チェック一覧

既存チェックは維持しつつ、**現在ループは厳格・未来ループは"促し(info)"** で運用（未来の宣言を叱らない）。

| # | 名称 | 重大度 | 条件 | 意図 |
|---|---|---|---|---|
| 既1' | 裏づけのない約束 | warn | `lifecycle_state='current'` の提供価値に `evidencedBy` 実績が無い | **current に限定**（従来の"約束は実績で"を現在ループだけに適用） |
| 既7 | 理念から辿れない要素 | info | 既存どおり | 現状体系の自己整合 |
| 新A | 未来の約束に獲得計画が無い | info | `lifecycle_state='target'` の提供価値に `toBeEvidencedBy`(DE) が無い | 未来の約束に道筋を促す |
| 新B | 理想に紐づかない獲得目標 | info | `desired_evidence` に `requires`(vision→) が無い | 孤立DEを検出 |
| 新C | 昇格レビュー待ち | info | 紐づくDEが全て `met` なのに提供価値が `target`/`transition_candidate` のまま | 「current 昇格を検討」動線 |
| 新D | 立証方法の欠落 | info | `desired_evidence` に `verification_method` も `achievement_rule` も無い | 判定不能なDEを検出 |
| 新E | 宙に浮いた立証 | info | `verifies` の実績かDEの端点が解決不能（削除済み等） | 既存"宙に浮いた関係"の拡張 |

**採らないチェック（陳腐化・休眠を避ける）:** 「transition_candidate が長期滞留」等の"経過日数"系は入れない（撤去済みの証拠鮮度チェックと同じ轍）。

**ウィザード完了判定への影響:** 完了判定は現行どおり `uncoveredWarnCount`（＝current の裏づけ欠落）ベース。新チェックは全て info なので**完了判定を邪魔しない**。

## 6. 実証進捗の計算仕様（旧「到達度」）

**表示名：「理想像の実証進捗」（第一候補）／「証拠獲得進捗」。** "ブランドが何％完成"の断定は避ける。**常に動的算出・非保存**（既存原則「derived=表示・保存しない」）。

### 6-1. DE単位の達成率 `frac(DE)`（0〜1）

`achievement_state_override` があればそれを優先し `met=1 / partially_met=0.5 / unmet=0`。無ければ `achievement_rule` で判定：

| rule.type | 判定 | frac |
|---|---|---|
| `count` (threshold N) | `verifies` 実績数 v | `min(1, v / N)`（v≥N で met=1、0<v<N で partially_met、0で unmet） |
| `value` (op,target) | `target_value` と実績側の値の比較 | `min(1, 実測 / target_value)`（op基準で met 判定） |
| `boolean` | verifies 実績が1件以上 | 有＝1(met) / 無＝0(unmet) |
| 未設定 | 離散フォールバック | verifies 有=0.5(partially) / 実行 done相当=1 は取らない（手動overrideのみmet） |

`partially_met`/`met`/`unmet` の**表示ラベルも frac から導出**（frac=1→met, 0<frac<1→partially_met, 0→unmet）。

### 6-2. 理想（vision）単位の実証進捗

対象 = その vision が `requires` する DE 群（`execution_state='cancelled'` は分母から除外）。

```
実証進捗 = Σ_i ( importance_weight_i × frac(DE_i) )  /  Σ_i ( importance_weight_i )
```

- 重み付き平均。全DEが met で 100%。
- 表示は「実証進捗 72%（獲得目標の証拠 5件中、重み換算で72%を実証済み）」のような**証拠獲得の言い方**にする。
- 会社全体の値が欲しい場合は vision 横断で同式（分母＝全required DEの重み和）。

## 7. FACT / ASPIRATION の AI注入仕様

コピーAI・草案生成のプロンプトに、**事実と願望を物理分離**して渡す（反捏造の壁）。

| ブロック | 引用/断定 | 中身 |
|---|---|---|
| **FACT**（現有・引用可） | 可 | `proof_points`（実証済み事実）＋ `value_propositions` の `lifecycle_state='current'` |
| **ASPIRATION**（未来・断定引用禁止） | 不可（"目指す/これから"のみ） | `lifecycle_state IN (target, transition_candidate)` の提供価値 ＋ `desired_evidence`（未達/一部達成）＋ vision |

**ルール（既存 INTENT/FACT/RULES 分離と同強度）:**
- ASPIRATION の要素は、外向けコピーで**事実として引用・断定してはならない**。表現は「目指す」「これから」等の未来形に限定。
- `transition_candidate`（DEはmetだが未昇格）は**保守的に ASPIRATION 側**に置く（＝まだ"恒常提供できる事実"として断定させない）。昇格レビューで `current` になって初めて FACT へ移る。
- `desired_evidence` が `met` でも、**引用できるのは紐づく `proof_points`（＝事実）**であって DE 自体ではない（DEは目標概念）。
- 実装は `lib/copy/ontology-blocks.ts` の現行 FACT/INTENT 構築に ASPIRATION ブロックを追加し、`buildCopySystemPrompt`（role-matrix）へ渡す。**0件・未設定なら従来どおり**（フォールバックで挙動不変）。

## 9. B案へ移行する際の拡張ポイント

C案は「DEを一級に据える」ことで、B案へ**加算的に昇格**できるよう設計している。

| 拡張 | C案（初期） | B案（正規） | 移行の勘所 |
|---|---|---|---|
| 理想像 | vision を `requires` の起点に流用 | **`desired_brand_states` 独立テーブル**（顧客/社会/従業員からどう認識されたいか＝Visionと別概念） | ElementKindに `desired_brand_state` 追加。`requires` の source を vision→DBS に張り替え（データ移行スクリプトで既存 vision→DBS 生成 or 手動再設定）。**"Vision=理想のブランド像"と定義していない**ので概念衝突が起きない |
| 行動・節目 | `desired_evidence.milestone_note`（インライン） | **`milestones` テーブル**＋関係 `achievedThrough` | note を milestone 行へ分解。`achievedThrough`（DE→milestone）を relation に追加 |
| 達成条件 | `achievement_rule`(jsonb・簡易) | ルールエンジン/計測連携 | jsonb スキーマを拡張（後方互換キーで） |
| ペルソナ | 現在像のみ | 顧客の"なりたい姿"を接続 | persona に未来接続を追加 |
| Governance | draft/active/archived 任意 | 正式運用 | 独立に導入可 |

**設計上の担保:** `desired_evidence` を最初から独立テーブル＋関係接続にしてあるので、DBS/Milestone を足しても DE を作り直さずに済む（関係の張り替えで済む）。

## 10. 加算マイグレーションの実施順序（dual-run・全既定値で挙動不変）

過去の理念オントロジー移行と同じ作法（ローカル.sql先行→適用→記録・NOTIFY reload・破壊的変更なし）。

1. **`desired_evidence` テーブル作成**（RLS有効・service_role運用・FKにindex・全カラム既定値）。ElementKind／端点検証トリガに `desired_evidence` を追加。→ この時点で見た目・挙動は完全に不変（空テーブル）。
2. **`value_propositions.lifecycle_state`（default current）＋ promoted_by/at 追加**。→ 既存VPは全て current＝従来表示のまま。NOTIFY pgrst reload。
3. **`element_relations.relation_type` に aspiresTo/requires/toBeEvidencedBy/verifies を許可**（enum/CHECK拡張・既存行不変）。
4. **整合性チェック更新**（`lib/brand/integrity.ts`）：既1を current-scoped に、新A〜Eを info で追加。到達度＝実証進捗の算出関数を追加（read専用）。
5. **コピーAI FACT/ASPIRATION 分離**（`lib/copy/ontology-blocks.ts`）：ASPIRATION ブロック追加。0件フォールバックで従来挙動維持。
6. **superadmin UI**（未来設計タブ＋VP lifecycleトグル＋関係4種＋DE編集）。
7. **ID INC. で1本通し検証**：vision → requires → DE（重み・achievement_rule）→ verifies 実績 → 実証進捗、および target 提供価値 → transition_candidate → 昇格レビュー → current。コピー/整合性の before/after を確認。
