## 2. 契約（include-bz spec §3.2 の転記・これを厳守）

- **Method / Path**: `POST /api/external/brand-ontology`（本番 `https://branding.bz/api/external/brand-ontology`）
- **Headers**: `Authorization: Bearer <BRANDING_BZ_API_SECRET>` / `Content-Type: application/json`
- **Request**: `{ "companyId": "<uuid>", "personaId"?: "<uuid>" }`
- **Response 200**:

```ts
{
  version: 1                    // 固定
  companyId: string
  fetchedAt: string             // ISO8601
  companyName: string | null

  intent: string                // 理念・意図（引用禁止素材）
  facts: string                 // 検証可能な事実・実績
  aspiration: string            // 将来・ビジョン（断定不可）
  persona: string               // ターゲットペルソナ

  voice: {
    slogan: string | null
    toneRules: string[]
  }
  governance: {
    bannedTerms: string[]
    complianceNotes: string[]
  }
  proofIds: string[]
}
```

- **エラー**: `401`（秘密不一致 / **秘密未設定**）, `400`（companyId 不正）, `404`（company 不在）, `500`。

**★返さないもの（重要）**: `CopyOntologyBlocks` の `factText` / `intentStrings` / `quotablePhrases` / `painPoints` は**返さない**。これらは branding.bz 内部の生コーパスで、Stage3 判定用の実装詳細。契約に含めると内部型に外部が結合する。**上表のフィールドだけを返すこと。**

## 3. マッピング表（`buildCopyOntologyBlocks` の戻り値 → 契約）

`buildCopyOntologyBlocks(companyId, personaId)`（`lib/copy/ontology-blocks.ts:158-161`）はそのまま呼ぶ。内部で `getSupabaseAdmin()` を自前生成するのでクライアント引数は不要。

| 契約フィールド | 由来 | 追加クエリ |
|---|---|---|
| `intent` | `intentBlock` | 不要 |
| `facts` | `factBlock` | 不要 |
| `aspiration` | `aspirationBlock` | 不要 |
| `persona` | `personaBlock` | 不要 |
| `governance.bannedTerms` | `bannedTerms`（配列そのまま） | 不要 |
| `proofIds` | `injectedProofIds` | 不要 |
| `companyName` | `companies.name_ja ?? companies.name` | **要** |
| `voice.slogan` | `brand_guidelines.slogan` | **要** |
| `voice.toneRules` | `governance_rules` where `rule_type='tone_rule'` の `rule_text[]` | **要** |
| `governance.complianceNotes` | `governance_rules` where `rule_type='compliance_rule'` の `rule_text[]` | **要** |
| `version` / `fetchedAt` | `1` / `new Date().toISOString()` | – |

追加クエリは 3 本（`companies` / `brand_guidelines` / `governance_rules`）。いずれも `getSupabaseAdmin()` で `company_id` 絞り、`sort_order` 昇順。`governance_rules` は 1 回のクエリで取って `rule_type` で振り分ければ 2 本に収まる。

> 参考: `governance_rules.rule_type` の CHECK 制約は `banned_word / discouraged_expression / tone_rule / claim_rule / compliance_rule`（`supabase/migrations/20260608000000_create_proof_points_and_governance_rules.sql:51-68`）。今回使うのは `tone_rule` と `compliance_rule` の 2 種。

## 4. 認証 — **fail-closed** で実装する（ここだけ既存を真似ない）

既存の `app/api/cron/brand-score-snapshot/route.ts:15-21`（判定本体は `:17-19`）は共有秘密パターンだが **fail-open**（`if (cronSecret && ...)` ＝ env 未設定なら素通り）。**この形をコピーしないこと。**

> 行番号は `main` の 2026-08-09 時点（`93636b7` 相当の pull 後）で実測・検証済み。

```ts
function verifyServiceToken(request: NextRequest): NextResponse | null {
  const secret = process.env.BRANDING_BZ_API_SECRET
  // ★ fail-closed: 秘密が未設定なら常に拒否する（素通りさせない）
  if (!secret) {
    return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })
  }
  const authHeader = request.headers.get('authorization')
  if (authHeader !== `Bearer ${secret}`) {
    return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })
  }
  return null // OK
}
```

- `requireSuperadmin`（`app/api/superadmin/copy/review/route.ts:16-41`）は**使わない**。あれはユーザーセッション用で、サーバー間呼び出しには JWT が無い。
- レスポンスに内部エラー詳細（スタック・SQL）を含めない。
- **秘密は絶対に `NEXT_PUBLIC_` を付けない**（サーバー専用）。

## 5. 実装スケルトン

```ts
// app/api/external/brand-ontology/route.ts
import { NextRequest, NextResponse } from 'next/server'
import { getSupabaseAdmin } from '@/lib/supabase-admin'
import { buildCopyOntologyBlocks } from '@/lib/copy/ontology-blocks'

export async function POST(request: NextRequest) {
  const denied = verifyServiceToken(request)
  if (denied) return denied

  const body = await request.json().catch(() => ({}))
  const companyId = typeof body.companyId === 'string' ? body.companyId.trim() : ''
  const personaId = typeof body.personaId === 'string' ? body.personaId.trim() : undefined
  if (!companyId) {
    return NextResponse.json({ error: 'companyId は必須です' }, { status: 400 })
  }

  const supabase = getSupabaseAdmin()

  const { data: company } = await supabase
    .from('companies')
    .select('id, name, name_ja')
    .eq('id', companyId)
    .maybeSingle()
  if (!company) {
    return NextResponse.json({ error: 'company が見つかりません' }, { status: 404 })
  }

  const [blocks, guideline, rules] = await Promise.all([
    buildCopyOntologyBlocks(companyId, personaId),
    supabase.from('brand_guidelines').select('slogan').eq('company_id', companyId).maybeSingle(),
    supabase
      .from('governance_rules')
      .select('rule_type, rule_text')
      .eq('company_id', companyId)
      .in('rule_type', ['tone_rule', 'compliance_rule'])
      .order('sort_order'),
  ])

  const ruleTexts = (t: string) =>
    (rules.data ?? []).filter(r => r.rule_type === t).map(r => r.rule_text).filter(Boolean)

  return NextResponse.json({
    version: 1,
    companyId,
    fetchedAt: new Date().toISOString(),
    companyName: company.name_ja ?? company.name ?? null,
    intent: blocks.intentBlock,
    facts: blocks.factBlock,
    aspiration: blocks.aspirationBlock,
    persona: blocks.personaBlock,
    voice: {
      slogan: guideline.data?.slogan ?? null,
      toneRules: ruleTexts('tone_rule'),
    },
    governance: {
      bannedTerms: blocks.bannedTerms ?? [],
      complianceNotes: ruleTexts('compliance_rule'),
    },
    proofIds: blocks.injectedProofIds ?? [],
  })
}
```

## 6. env と共有秘密の手配（**コードでカバーされない運用作業・忘れやすい**）

| env | 設定先 | 用途 |
|---|---|---|
| `BRANDING_BZ_API_SECRET` | **branding.bz**（検証側）と **include-bz**（送信側）の**両方**に**同一値** | Bearer 共有秘密 |
| `BRANDING_BZ_API_URL` | include-bz のみ | `https://branding.bz/api/external/brand-ontology` |
| `BRANDING_BZ_SELF_COMPANY_ID` | include-bz のみ | `d57a4cea-3ee0-4254-8522-14a5e89d9034`（ID INC.） |

手順:
1. 秘密を生成（例 `openssl rand -hex 32`）。
2. branding.bz の Vercel（Production / Preview）に `BRANDING_BZ_API_SECRET` を設定。
3. include-bz の Vercel に同一値 ＋ 残り 2 つを設定。
4. ローカル用に両リポの `.env.local` にも設定。`.env.example` にはキー名のみ追記（値は書かない）。
5. **秘密値は Git にも公開 Drive にもコミットしない**（各自の手元管理）。

> 片側だけ設定すると 401 で全滅し、include-bz 側は「オントロジー未連携」として静かに一般基準生成に落ちる（生成は止まらない）。**症状が出にくいので、デプロイ時に両側揃っているか必ず確認すること。**
