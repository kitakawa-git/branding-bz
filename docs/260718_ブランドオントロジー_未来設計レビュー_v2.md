# ブランドオントロジー 未来設計レビュー v2

**作成日:** 2026-07-18
**位置づけ:** v1（同日）へのフィードバックを反映した再設計レビュー。コード変更はまだ行わない。設計の意味論を固め、実装3案を比較するところまで。
**v1からの主な更新:**
1. Proof Point は「すでに発生し検証可能な事実」に限定（`planned` を持たせない）。将来の証拠は独立概念 **Desired Evidence** に分離。
2. 「理想→実証」のライフサイクルを明示的にモデル化。
3. 関係型を `aspiresTo` / `requires` / `toBeEvidencedBy` / `achievedThrough` / `realizes` ＋既存 `evidencedBy` で再整理。
4. 状態は**一律の `time_stance` を廃止**し、概念ごとに意味の合う状態を持たせる。
5. Brand Gap は**動的算出を基本**とし、静的リレーション保存は非推奨。
6. 実装3案（A 最小変更 / B 意味論優先 / C 実装優先）を10観点で比較。

## 1. 意味論の修正（v1の誤り訂正）

v1は `proof_point.proof_status = planned` で未来を表そうとしたが、これは **「まだ存在しない証拠」を Proof Point と呼ぶ**ことになり、事実・実績・計画が同じ器に混ざる。オントロジーとして不健全。

**修正方針：**
- **Proof Point ＝ すでに発生し、検証可能な事実のみ。** 状態フラグを持たせない（常に"実証済み"）。コピーAIの唯一の引用元という現行の強みもそのまま。
- 将来的に獲得すべき証拠・達成条件は、**独立エンティティ `desired_evidence`（仮称）** として分離する。
  - 候補名の検討：Desired Evidence / Evidence Target / Proof Target / Achievement Criterion / Brand Milestone。
  - **採用：`desired_evidence`（表示名「獲得目標の証拠」）。** 理由：Proof Point と対（現有↔獲得予定）で語れて分かりやすく、「Milestone（行動・節目）」とは別レイヤー（＝証拠そのものと、証拠を得る行動は分ける）に保てる。

こうすると「事実（Proof Point）」「目標の証拠（Desired Evidence）」「行動・節目（Milestone）」の3つが混ざらない。

---

## 2. ライフサイクル設計（理想 → 実証のループ）

指定の6ステップを、エンティティと関係で表す。

```
① 理想状態を定義
      Desired Brand State（理想のブランド像）
          │ requires
② 必要な証拠を定義
      Desired Evidence（獲得目標の証拠）   ← state: planned
          │ achievedThrough
③ 獲得の行動・節目を設定
      Milestone / Action                  （DE state → in_progress）
          │  （実行）
④ 成果が発生 → 事実を登録
      Proof Point（実証済み事実のみ）
          │ realizes
⑤ 実績が「獲得目標の証拠」を実現したと判定
      Proof Point ─realizes→ Desired Evidence   （DE state → achieved）
          │
⑥ 理想状態への到達度を更新（動的算出）
      Desired Brand State.到達度 = achieved DE数 / required DE数
```

**現在ループ（既存・不変）：** Value Proposition〈current〉 ─`evidencedBy`→ Proof Point。「今できる約束は、実績で裏づく」。

**未来ループ（新規）：** Value Proposition〈target〉 ─`toBeEvidencedBy`→ Desired Evidence ─`achievedThrough`→ Milestone …（成果）… Proof Point ─`realizes`→ Desired Evidence（achieved）。「未来の約束は、獲得予定の証拠を必要とし、行動で得て、成果が出たら事実になり、その事実が証拠を実現する」。

この2ループが Proof Point で**合流**するのがポイント。未来の計画は、達成された瞬間に「事実（Proof Point）」へと姿を変え、現在ループに合流する。

## 3. エンティティと「概念ごとの状態」（一律 time_stance の廃止）

v1の「全要素に time_stance」は乱暴だった。**状態は概念の性質に合わせて個別に持たせる**。

| 概念 | 状態（ライフサイクル） | 理由 |
|---|---|---|
| Vision / **Desired Brand State**（理想像） | 本質的に未来。持つのは進捗系のみ（`proposed` / `active` / `achieved` / `revised`） | 未来そのものなので「現在/未来」タグは不要。あるのは"どこまで達成したか" |
| **Proof Point**（実績） | **状態なし（常に実証済み事実）** | 事実のみ。plannedは持たせない |
| **Desired Evidence**（獲得目標の証拠・新規） | `planned` / `in_progress` / `achieved` | 証拠獲得の進捗 |
| **Value Proposition**（提供価値） | `current` / `target` / `transitional` | 今できる約束か、目指す約束か |
| **Governance Rule**（表現ルール） | `draft` / `active` / `archived` | ルールの運用状態（未来設計とは独立に有用） |
| Philosophy: mission / values / 行動指針 | 状態なし（不変の芯） | 恒常。時制の概念になじまない |
| Persona（顧客像） | 今回は状態なし（現在の観察） | スコープ外。将来「顧客のなりたい姿」を足す余地はある |
| **Milestone / Action**（節目・行動・新規） | `todo` / `doing` / `done` | 実行の進捗 |

ポイントは、**「時制」を1本のカラムで表さない**こと。Vision は未来"しか"ない、Proof Point は事実"しか"ない、と概念ごとに意味が違うので、状態語彙も概念ごとに分ける。

## 4. 関係型の再整理

既存6種（`guides` / `evidencedBy` / `promisedTo` / `communicatedAs` / `constrainedBy` / `conflictsWith`）に、未来ループの5種を足す。指定の関係型を採用し、意味を確定する。

| 関係 | 起点 → 対象 | 自然文 | 時制 |
|---|---|---|---|
| `aspiresTo` | 現状（company / Value Prop〈current〉） → Desired Brand State | 「A は B を目指す」 | 未来 |
| `requires` | Desired Brand State → Desired Evidence | 「理想 A の実現には B が必要」 | 未来 |
| `toBeEvidencedBy` | Value Proposition〈target〉 → Desired Evidence | 「未来の約束 A は B で裏づけられる予定」 | 未来 |
| `achievedThrough` | Desired Evidence → Milestone / Action | 「証拠 A は行動 B で獲得する」 | 未来 |
| `realizes` | Proof Point → Desired Evidence | 「実績 A が、目指していた証拠 B を実現した」 | 達成時＝現在 |
| `evidencedBy`（既存） | Value Proposition〈current〉 → Proof Point | 「今の約束 A は実績 B に裏づけられる」 | 現在 |

**対称性（設計の美点）：** 現在は `evidencedBy`（約束→実績）、未来は `toBeEvidencedBy`（約束→獲得目標の証拠）。`realizes`（実績→獲得目標の証拠）が両者の橋になる。

**反捏造の壁（最重要・維持）：** `target` の約束・`desired_evidence`・`Desired Brand State` は、外向けの**断定・事実引用に使えない**。使えるのは「目指す／これから」の宣言のみ。コピーAIには FACT（現有＝Proof Point・current約束）と ASPIRATION（未来＝target・desired_evidence）を**物理分離**して渡す。＝未来を扱ってもウソにならない。

## 5. Brand Gap の扱い（保存 vs 算出 vs 独立エンティティ）

ギャップは「現状と理想の比較結果」。それを**どう持つか**を3案で比較。

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| (a) `gapWith` を関係で保存 | 現状↔目標のギャップを静的エッジに | 明示的で見やすい | **陳腐化**。証拠が増える／目標が変わるたびに手動同期が要る。撤去済みの「証拠鮮度チェック」と同じ轍（休眠・ズレ） |
| (b) **動的算出（推奨）** | 到達度 = achieved DE数 ÷ required DE数 を read 時に計算 | 常に最新・保存ゼロ・整合性崩れない | 定量のみ。"どんなギャップか"の定性記述は持てない |
| (c) 独立 Brand Gap エンティティ | 差分を独立ノードに（定性ナラティブ＋紐づくDE） | 戦略的な差分を言語化・注釈できる | 二重管理・同期の手間 |

**推奨：定量（到達度）は (b) 動的算出。** これは本プロジェクトの既存原則「**derived（派生値）= 表示。保存しない**」に一致（cf. ペルソナの description 派生・到達度スナップショット）。
**定性の記述が欲しい局面のみ (c) を軽量オプション**として足す（**数値は持たせず算出**・ナラティブだけ保存）。
**(a) の `gapWith` 保存は非推奨**（陳腐化リスクが実害として既に経験済み）。

## 6. 実装3案の比較

### A. 最小変更案 — 既存構造を最大限維持

- **エンティティ構造**：新テーブルを作らない。`desired_evidence` は独立させず、Value Proposition〈target〉に「獲得したい証拠」をメモ的フィールドで持たせる程度。Desired Brand State は既存 vision を流用。
- **関係型**：`aspiresTo` のみ追加（現状→vision）。`requires`/`toBeEvidencedBy`/`achievedThrough`/`realizes` は入れない（未来ループを組まない）。
- **DB変更**：`value_propositions.time_stance` 1本＋テキスト列1本程度。
- **既存データ移行**：ほぼ不要（既定 `current`）。
- **コピーAIへの影響**：target 約束を ASPIRATION として分離注入する分岐を1つ足すだけ。
- **整合性チェック**：チェック1を time_stance で分岐（current のみ warn）。新チェックなし。
- **UI変更**：提供価値編集に時制トグル1つ。
- **将来拡張性**：低。Desired Evidence が一級でないので、ライフサイクル⑤⑥（realizes・到達度）が組めない。後で作り直しになる。
- **実装コスト**：小。
- **意味論リスク**：**高**。北川さん指摘の「事実・計画の混在」を"メモ列"の形で温存してしまう。今回の問題意識に正面から応えられない。

### B. 意味論優先案 — オントロジーとして整合

- **エンティティ構造**：`desired_brand_states` / `desired_evidence`（state付き）/ `milestones`（state付き）を新設。Proof Point は事実限定のまま。Value Proposition に time_stance。
- **関係型**：`aspiresTo` / `requires` / `toBeEvidencedBy` / `achievedThrough` / `realizes` を全部入れ、未来ループを完全表現。既存6種と併存。
- **DB変更**：新テーブル3＋列追加数本＋`element_relations.relation_type` enum拡張。
- **既存データ移行**：加算的（既存は current/proven のまま）。新テーブルは空スタート。
- **コピーAIへの影響**：FACT / ASPIRATION の物理分離を本実装（現有＝Proof Point・current、未来＝desired_evidence・target）。
- **整合性チェック**：時制分岐＋新チェック（「未来の約束に toBeEvidencedBy が無い」「Desired Evidence に achievedThrough が無い」「realizes 済みなのに DE が achieved でない」等）＋到達度算出。
- **UI変更**：理想像・獲得目標の証拠・マイルストーンの編集画面（superadmin）を新設。関係オーサリングに新5種。
- **将来拡張性**：**高**。ライフサイクル全6ステップが素直に乗る。ペルソナの未来像など拡張余地も。
- **実装コスト**：**大**（新テーブル3＋UI3画面＋チェック多数）。
- **意味論リスク**：低（最も整合）。ただし**過剰設計リスク**：使われない Milestone/DE が並ぶと運用が形骸化する恐れ。

### C. プロダクト実装優先案 — 現実的な中庸（推奨）

- **エンティティ構造**：`desired_evidence`（state: planned/in_progress/achieved・**Milestoneはこの中にインライン**＝別テーブルにしない）を1つ新設。**Desired Brand State は新テーブルを作らず、既存 vision（philosophy_elements）を"理想像アンカー"として流用**（必要になったら後で昇格）。Value Proposition に time_stance。Proof Point は事実限定のまま。
- **関係型**：`aspiresTo`（現状→vision）/ `requires`（vision→DE）/ `toBeEvidencedBy`（target VP→DE）/ `realizes`（Proof Point→DE）を採用。`achievedThrough` は DE 内のマイルストーン欄で代替（関係を増やしすぎない）。
- **DB変更**：新テーブル1（`desired_evidence`）＋`value_propositions.time_stance`＋relation_type enum に4種。
- **既存データ移行**：加算的・既存不変。
- **コピーAIへの影響**：B と同じ FACT/ASPIRATION 分離（現有=Proof Point/current、未来=desired_evidence/target VP）。
- **整合性チェック**：時制分岐＋新チェック2つ（「target 約束に toBeEvidencedBy 無し」「realizes 済みで DE 未 achieved」）＋到達度の動的算出（vision 単位）。
- **UI変更**：superadmin に「獲得目標の証拠（DE）」タブ1枚＋提供価値の時制トグル＋関係に4種追加。理想像は vision 編集を流用。
- **将来拡張性**：中〜高。DE が一級なのでライフサイクルは回る。Desired Brand State / Milestone を独立させたくなったら **B へ無理なく昇格**できる（DEを軸に据えたため）。
- **実装コスト**：中。
- **意味論リスク**：低〜中。「理想像＝vision流用」がやや簡略だが、意味の混在（事実↔計画）は起きない（DEを分離したので核心は満たす）。

## 7. おすすめ

- **C を実装ターゲット、B を北斗（forward-compatible の指針）に。** C は「Proof Point＝事実・Desired Evidence＝独立」という北川さんの核心指摘を満たしつつ、Desired Brand State / Milestone の独立を"後で昇格"に回してコストを抑える。DE を軸に据えるので、後から B へ滑らかに広げられる。
- **A は不採用寄り。** 実装は軽いが、"事実と計画の混在"を別の形（メモ列）で温存し、今回の問題意識に応えない。
- **最初の実験は ID INC. 自社ブランド。** 理想像（vision）→ requires → 獲得目標の証拠（DE）→ 行動 → 成果（Proof Point）→ realizes → 到達度、を1本通し、コピー/整合性の before/after を見る。
