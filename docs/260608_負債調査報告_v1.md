## 調査A: wide-open RLS の棚卸し

### A.1 wide-open ポリシー一覧（`pg_policies` 全件から抽出）

「wide-open」= 書き込み系コマンドが `USING(true)/WITH CHECK(true)`（テナント境界なし）。

#### 分類1: `auth_all`（FOR ALL TO authenticated USING(true) WITH CHECK(true)）= 全操作無制限
`admin_users`, `brand_color_projects`, `brand_personality_tag_mappings`, `brand_quizzes`, `brand_quiz_questions`, `brand_quiz_attempts`, `brand_quiz_answers`, `brand_surveys`, `brand_survey_questions`, `brand_score_snapshots`, `goal_kpis`, `goal_periods`, `mini_app_sessions`, `mini_app_conversations`, `value_propositions`
（15テーブル。**任意の認証ユーザーが全社のデータを読み書き可能**）

#### 分類2: 公開SELECT + authenticated書き込み無制限（`public_select` + `auth_write_*`）
`companies`, `news`, `profiles`
（SELECTは anon 含む公開〔/card・/news 用〕、INSERT/UPDATE/DELETE は authenticated 無制限）

#### 分類3: 匿名INSERT受付 + authenticated SELECT/UPDATE/DELETE無制限（`anon_insert` + `auth_*`）
`card_events`, `card_views`, `brand_page_views`, `brand_micro_feedbacks`, `brand_survey_responses`, `survey_participants`
（匿名トラッキング/サーベイ回答のため anon INSERT は**意図的**。読取・更新・削除が authenticated 無制限なのが論点）

#### 参考: 既に適切にスコープ済み（＝wide-openではない・移行の手本）
`brand_guidelines`(admin書込/scoped select+public select), `brand_visuals`(同), `brand_personalities`(admin書込/scoped), `brand_personas`(admin_all/scoped), `brand_terms`(admin_all/scoped), `members`(admin書込/self+admin select), `invite_links`, `announcements`/`announcement_*`(admin書込・user scoped), `timeline_*`(user scoped), `personal_goals`(user scoped), `contact_inquiries`(anon insert/superadmin select), `proof_points`/`governance_rules`(Step 0・superadmin書込/member select)

### A.2 緊急パッチがなぜ必要だったか（**最重要**）

マイグレーション `supabase/migrations/20260430000000_enable_rls_emergency_patch.sql` の**ヘッダコメントに理由が明記**されている。git 履歴とも整合。

> 目的:
> 1. Supabase Advisor の `rls_disabled_in_public` / `sensitive_columns_exposed` ERROR を解消する
> 2. 未認証 (anon) ロールからの破壊的書き込みを遮断する
> 3. 既存アプリ (anon JWT を持つ認証ユーザー) を壊さない
>
> 注意: "auth_*" 系のポリシーは authenticated 全許可 (USING true) でテナント境界を担保しない**暫定実装**。**Step 3 で auth.uid()/company_id ベースの細かいポリシーに置き換える**。

**経緯（git）:**
- `feature/rls-step1` ブランチ（PR #1, #2）で実施。
- `e0fdc2b fix(api): RLS対応のためAPI Routeをservice_role化` → 一部APIをservice_role化した上で、
- `f44df38 feat(db): RLS緊急パッチmigration追加(20テーブル+47ポリシー)` でRLSを一括有効化。

**つまり**: それ以前は **RLSが無効**で、Advisorが `rls_disabled_in_public`（RLS無効）と `sensitive_columns_exposed`（anon に機微列が露出）を ERROR 判定していた。これを**最短で解消しつつ既存アプリを壊さない**ために、`USING(true)` の暫定ポリシーで「RLS有効＋anon書込遮断」だけを満たした。本来の per-tenant 化（命名上の "Step 3"）は計画されたが**未実施のまま現在に至る**。

**引き締め時の必須教訓**: 当時 `USING(true)` を選んだ理由は **既存アプリが多数のテーブルへ「authenticatedクライアント直書き / REST(Bearer)」で書き込んでいた**ため。これを `company_id` 境界に絞ると、該当アプリ経路が壊れる。よって**書き込み経路の特定（A.3）が引き締めの前提**。理由を踏まえず一律に絞ると同じ障害（書き込み不能）が再発する。

### A.3 各テーブルの書き込み経路と分類

書き込みクライアント種別:
- **(s) service_role**: API Route内 `getSupabaseAdmin()`（RLSバイパス）→ RLS引き締めの影響を受けない
- **(c) クライアント直**: `@/lib/supabase`(anon key, 'use client') の `.insert/.update/.delete` → **RLS依存**
- **(r) REST直**: `fetch(${url}/rest/v1/...)` + Bearer（authenticated）→ **RLS依存**

| テーブル | 書き込み経路（代表） | 分類 |
|----------|----------------------|------|
| **admin_users** | (s) api/signup, api/superadmin/create-company のみ | **即引き締め可（最優先・セキュリティ）** |
| profiles | (s) api/signup, api/members | 即引き締め可（書込側。SELECTは公開維持） |
| brand_color_projects | (s) api/tools/colors/chat | 即引き締め可 |
| mini_app_conversations | (s) api/tools/colors/chat | 即引き締め可 |
| mini_app_sessions | (s) api/tools/colors/sessions 他 | 即引き締め可（ツール経路多数→回帰確認推奨） |
| brand_quiz_attempts / brand_quiz_answers | (s) api/brand-score/quizzes/[id]/attempt | 即引き締め可 |
| brand_quizzes / brand_quiz_questions | アプリ書込未検出（brand-score API=service_role想定） | 即引き締め可（書込経路の最終確認推奨） |
| brand_surveys / brand_survey_questions | アプリ書込未検出（同上） | 即引き締め可（同上） |
| brand_score_snapshots | アプリ書込未検出（cron=service_role） | 即引き締め可 |
| brand_personality_tag_mappings | アプリ書込未検出 | 即引き締め可 |
| **value_propositions** | (r) admin/brand/strategy（全削除→全INSERT） | **アプリ改修が必要**（brand_terms方式へ） |
| **companies** | (c) superadmin/companies/[id] update ＋ (r) admin/brand/strategy PATCH ＋ (s) signup | **アプリ改修が必要**（client書込経路あり） |
| **news** | (c) superadmin/news delete | **アプリ改修が必要** |
| **goal_kpis** | (c) portal/kpi, portal/page | **アプリ改修が必要** |
| **goal_periods** | (c) admin/kpi | **アプリ改修が必要** |
| card_views / card_events / brand_page_views / brand_micro_feedbacks / brand_survey_responses / survey_participants | 匿名INSERT（トラッキング/サーベイ）。読取は分析画面 | **保留推奨**（anon INSERT維持必須・SELECT絞りは読取経路調査後） |

#### 分類まとめ
- **即引き締め可**（書込が service_role のみ／クライアント書込なし）: `admin_users`(最優先), `profiles`(書込側), `brand_color_projects`, `mini_app_sessions`, `mini_app_conversations`, `brand_quiz_attempts`, `brand_quiz_answers`, `brand_quizzes`, `brand_quiz_questions`, `brand_surveys`, `brand_survey_questions`, `brand_score_snapshots`, `brand_personality_tag_mappings`
- **アプリ改修が必要**（クライアント/REST直書き → brand_terms方式 or 書込のservice_role化が前提）: `value_propositions`, `companies`, `news`, `goal_kpis`, `goal_periods`
- **保留推奨**: トラッキング6テーブル（理由: anon INSERT は仕様。SELECT/UPDATE/DELETE のテナント越境は是正したいが、(1) 分析画面の読取経路確認が必要、(2) 行数大〔card_views 474 / brand_page_views 2,637〕で影響範囲が広い）

#### ⚠ 重要セキュリティ所見（最優先で別途是正推奨）
- **`admin_users` が `auth_all`（FOR ALL authenticated USING(true)）**。＝**任意の認証ユーザーが生トークンで `admin_users` を INSERT/UPDATE 可能 → 自分を `is_superadmin=true` に昇格、または他社管理者を改ざんできる**。アプリの書き込みは全て service_role 経由なので、**クライアント書き込みを禁止しても既存機能は壊れない**＝低リスク・高効果。
- 分類1の各テーブルは**テナント越境の読み書き**が可能（例: 他社の `brand_surveys` / `goal_kpis` / `value_propositions` / `mini_app_sessions` を閲覧・改ざん可能）。現状テナント分離は **アプリ層（getAdminContextのcompany絞り）でのみ**担保され、DB層では未担保。

## 調査C: jsonbスキーマ揺れの実態

対象: `brand_guidelines.{values, action_guidelines, business_content, traits}`（全て jsonb 配列）。配列要素のキー構成を全9社分で集計。
（注: `traits` は `brand_personalities` にも同名列が存在するが、本調査は指示通り `brand_guidelines.traits` を対象）

| カラム | 要素キー構成（keysig） | 社数 | 要素数計 | 評価 |
|--------|------------------------|------|----------|------|
| **values** | `{description, value}` | 3 | 9 | ← 旧形式（`value` キー） |
| | `{added_index, description, name}` | 2 | 7 | ← 新形式（`name` キー） |
| | (空配列) | 1 | 0 | |
| **action_guidelines** | `{title, description}` | 5 | 27 | **統一済み（良好）** |
| | (空配列) | 1 | 0 | |
| **business_content** | `{added_index, description, title}` | 3 | 7 | `added_index` 有無の差 |
| | `{description, title}` | 3 | 7 | |
| **traits** | `{description, name, score}` | 2 | 8 | 基本形 |
| | (空配列) | 2 | 0 | |
| | `{added_index, copy, description, name, score}` | 1 | 5 | `copy` 追加 |
| | `{added_index, description, name, score}` | 1 | 4 | `added_index` 追加 |

**Step 1正規化に向けた所見**:
- **`values` が最重要**: 同一概念に対し **`value` キー（3社）と `name` キー（2社）の非互換2形態**。要素ID化の前に**キー名統一**（`name` + `description` + 任意 `added_index` への寄せ等）が必要。表示/編集両コードの同時対応を要する。
- **`traits`**: 基本 `{name, description, score}` に対し `copy`(1社) / `added_index`(2社) が混在。`copy` は trait のキャッチコピー（`lib/brand-mvv.ts` の `resolveTraitCopy` が copy/description 揺れを吸収中＝コード側で既に揺れを認識）。
- **`business_content`**: `added_index` の有無のみ（軽微）。
- **`action_guidelines`**: `{title, description}` で統一済み（正規化不要）。
- **`added_index`**: values/business_content/traits の一部に出現。UIの「項目追加」が付与したインデックス痕跡と推定。正規化時に整理対象。

## 是正推奨順序（リスク低 → 高）

| # | アクション | リスク | 効果 | 種別 |
|---|-----------|--------|------|------|
| 1 | **`admin_users` の書き込み引き締め**（client書込禁止・service_roleのみ許可へ） | 低（app影響なし） | 高（superadmin自己昇格を封鎖） | A・セキュリティ |
| 2 | service_role-only テーブル群の引き締め（brand_color_projects / mini_app_* / brand_quiz_* / brand_survey_* / brand_score_snapshots / brand_personality_tag_mappings / profiles書込） | 低（要brand-score書込経路の最終確認） | 中（テナント越境の書込封鎖） | A |
| 3 | `companies.brand_story` を退避の上 DROP（dead） | 低 | 低（スキーマ整理） | B |
| 4 | `companies.provided_values` を value_propositions に片寄せ → DROP | 低 | 低 | B |
| 5 | `companies.slogan` / `mvv` を brand_guidelines へ片寄せ（superadmin編集の向き先修正＋表示一致）→ DROP | 中（UI改修） | 中（**no-op編集の不具合解消**） | B |
| 6 | jsonb `values` の `value`/`name` キー統一マイグレーション（表示・編集コード両対応） | 中 | 高（Step 1の前提） | C |
| 7 | jsonb `traits`/`business_content` の `added_index`/`copy` 揺れ吸収・正規化 | 中 | 中 | C |
| 8 | クライアント直書きテーブルの brand_terms方式移行（value_propositions / news / goal_kpis / goal_periods / companies の client書込経路）。書込のservice_role化 or scopedポリシー＋UI/API改修 | 高（UI/API改修大・回帰広） | 高（テナント境界をDB層で担保） | A |
| 9 | トラッキング6テーブルの SELECT/UPDATE/DELETE をテナント絞り（anon INSERTは維持） | 中〜高（読取経路調査が前提） | 中 | A・保留解除 |

**原則**: A.2の教訓どおり、各引き締めは「書き込み経路（A.3）」を確認し、service_role経由のみのものから着手する。クライアント直書き経路は**先にアプリ側（service_role API化 or scopedポリシー対応UI）を用意してから**ポリシーを絞る。
