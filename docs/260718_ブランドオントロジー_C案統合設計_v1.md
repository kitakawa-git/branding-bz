## 0. スコープと原則

- **C案＝初期実装 / B案＝将来の正規モデル。** C は「現在（証拠つき）＋目標（理想）＋道のり（獲得すべき証拠）」を、最小の追加で表現する。
- **加算的・dual-run。** すべて既定値で従来挙動を維持。各段は単独で安全。破壊的変更はしない。
- **反捏造の壁を維持。** 目標（target/desired_evidence/vision）は外向けコピーで断定・事実引用しない。
- **事実は機械・語りはAI。** 達成判定はコードで決定論的に。AIには創作させない。
- **derived＝表示・保存しない。** 達成状態・進捗率は動的算出。保存するのは人間の判断のみ。
- **Vision ≠ 理想のブランド像。** Vision＝実現したい社会・事業の未来。「理想のブランド像（顧客・社会・従業員からどう認識されたいか）」は別概念（B案の `desired_brand_states`）。C案では vision をアンカーに運用するが、**「Vision＝理想のブランド像」とは定義しない**。

## 3. relation_type と achievement_rule

### 3-1. relation_type 確定

既存6種（`guides`/`evidencedBy`/`promisedTo`/`communicatedAs`/`constrainedBy`/`conflictsWith`）不変。追加4種：

| relation_type | 起点 → 対象 | 自然文 | 備考 |
|---|---|---|---|
| `aspiresTo` | value_proposition〈target〉/philosophy → philosophy(vision) | 「A は B（理想）を目指す」 | 任意 |
| `requires` | philosophy(vision) → desired_evidence | 「理想 A の実現には B が必要」 | |
| `toBeEvidencedBy` | value_proposition〈target〉 → desired_evidence | 「未来の約束 A は B で裏づく予定」 | |
| `verifies` | proof_point → desired_evidence | 「実績 A は、獲得目標 B の達成を立証する」 | **管理者による立証根拠の採用**（下記） |

**`verifies` の意味（明文化）:** 単なる関連付けではなく、**「この実績を、この獲得目標の立証根拠として管理者が採用する」行為**。関係の作成＝管理者承認とみなす（C案の簡略化）。誤紐付けが即 met にならないための前提。将来（B案）は関係自体に `verification_status`/`verified_by`/`verified_at`/`verification_note` を持たせ二段階承認に拡張。

### 3-2. `achievement_rule` スキーマ

```ts
type AchievementRuleV1 =
  | { version: 1; type: "boolean"; minimum_proof_count?: number }
  | { version: 1; type: "count";
      threshold: number;
      metric_filter?: { metric_key: string; unit?: string; operator?: ">=" | "<="; value?: number } }
  | { version: 1; type: "aggregate";
      metric_key: string;
      aggregation: "sum" | "average" | "maximum" | "minimum" | "latest";
      unit: string;
      operator: ">=" | "<=";
      target: number;
      baseline?: number }
  | { version: 1; type: "manual" };
```
- 明示語彙（`aggregation`/`operator`/`average`/`maximum`/`minimum`）。演算子は **`>=` と `<=` のみ**。
- UI表示：`boolean` は「立証実績の存在／必要な実績数」と表示（追加・利用者向け表現）。

### 3-3. `achievement_rule` バリデーション（追加③）

| 対象 | 条件 | 違反時 |
|---|---|---|
| 共通 | `version=1`／`importance_weight>0`／`progress_fraction∈[0,1]`／`metric_value` は有限値 | 入力エラー |
| boolean | `minimum_proof_count>=1`（省略時1） | 入力エラー |
| count | `threshold>=1`／`metric_filter.operator` があれば `value` 必須／`value` があれば `operator` 必須 | 入力エラー |
| aggregate | `metric_key` 非空／`unit` 非空／`target` 有限 | 入力エラー |
| aggregate baseline | `operator=">="` なら `baseline < target`／`operator="<="` なら `baseline > target` | **`INVALID_BASELINE`**（進捗を算出しない・§5-3）。`baseline==target` は特例処理せず入力エラー |

## 4. 判定結果の構造

```ts
type AchievementEvaluation = {
  state: "unmet" | "partially_met" | "met" | "indeterminate";
  progress_fraction: number | null;      // baseline無し等は null
  source: "automatic" | "manual";
  evaluated_value: number | null;        // aggregate 集計結果など
  matched_measurement_count: number;     // 判定に使えた実績/測定値の件数
  reason_code: string;
};
```
**state（達成か）＝演算子×目標。progress_fraction（どこまで）＝baseline→target。両者は別物。** `>=`/`<=` 限定で境界矛盾なし。

reason_code: `MET` / `BELOW_TARGET` / `INSUFFICIENT_COUNT` / `NO_MATCHING_MEASUREMENT` / `NO_MEASURED_DATE` / `INVALID_RULE` / `INVALID_BASELINE` / `MANUAL_REVIEW` / `MANUAL_OVERRIDE`。

## 5. 判定アルゴリズム（自動評価エンジン）

```
function evaluate(DE) -> AchievementEvaluation:

  # 0) 有効な人間判断があれば優先（§6の失効判定を通ったものだけ）
  h = currentValidHumanJudgment(DE)          # §6-1
  if h exists:
     return { state:h.achievement_state, progress_fraction:h.progress_fraction,
              source:"manual", evaluated_value:null, matched_measurement_count:0,
              reason_code: h.evaluation_source=="manual_review" ? "MANUAL_REVIEW" : "MANUAL_OVERRIDE" }

  P = proofsAdoptedVia_verifies(DE)          # 端点解決済みのみ（幽霊エッジ除外）
  r = DE.achievement_rule
  if invalid(r): return indeterminate("INVALID_RULE")

  switch r.type:

    "boolean":
        n = |P|; need = r.minimum_proof_count ?? 1
        met = n >= need
        return { state: met?"met":"unmet", progress_fraction: met?1:0,
                 source:"automatic", evaluated_value:n, matched_measurement_count:n,
                 reason_code: met?"MET":"INSUFFICIENT_COUNT" }

    "count":
        # metric_filter を満たす測定値を持つ PP を、PP単位で distinct に数える（追加⑥）
        Pf = proofsWithQualifyingMeasurement(P, r.metric_filter)   # COUNT(DISTINCT proof_point_id)
        n = |Pf|
        state = n>=r.threshold ? "met" : (n>0 ? "partially_met" : "unmet")
        return { state, progress_fraction: clamp(n/r.threshold,0,1),
                 source:"automatic", evaluated_value:n, matched_measurement_count:n,
                 reason_code: state=="met"?"MET":"INSUFFICIENT_COUNT" }

    "aggregate":
        M = measurements(P) where metric_key==r.metric_key AND metric_unit==r.unit AND metric_value is finite
        if r.aggregation=="latest": M = M where measured_at != null
        if M empty:
           return indeterminate(r.aggregation=="latest" ? "NO_MEASURED_DATE" : "NO_MATCHING_MEASUREMENT")
        # 同一指標の測定値が複数（同一/別PP）ある場合の集約単位（追加・その他）:
        #   latest=measured_at最新1行 / sum=全該当合計 / average=全該当平均 / maximum,minimum=全該当から
        a = aggregate(M, r.aggregation)
        met = (r.operator==">=") ? a>=r.target : a<=r.target
        (frac, invalidBaseline) = progressFraction(a, r)     # §5-3
        if invalidBaseline: return { state: met?"met":"unmet", progress_fraction:null,
                 source:"automatic", evaluated_value:a, matched_measurement_count:|M|,
                 reason_code:"INVALID_BASELINE" }
        state = met ? "met" : (frac!=null && frac>0 ? "partially_met" : "unmet")
        # scope 混在の注意（追加・その他）: M に異なる measurement_scope が混在していれば info を別途発火
        return { state, progress_fraction:frac, source:"automatic",
                 evaluated_value:a, matched_measurement_count:|M|,
                 reason_code: met?"MET":"BELOW_TARGET" }

    "manual":
        return indeterminate("MANUAL_REVIEW")   # 人間判断が無い manual は「判定不能」（未達ではない）
```

### 5-1. 一致条件（key＋単位）
`aggregate`・`count(metric_filter)` の対象は **`metric_key` 一致 かつ `metric_unit` 一致**の測定値のみ。単位が同じでも別指標（認知率と解約率がともに%）は key で弾く。

### 5-2. indeterminate と unmet の区別
- **unmet**＝測れた／数えられた、しかし足りない。
- **indeterminate**＝測れない（測定値なし・key/単位不一致で対象空・rule不正・latestで測定日なし・manualで人間判断なし）。
- 「実績不足」と「データ不足」を混同しない。

### 5-3. progressFraction（baseline 自動補完しない）
```
progressFraction(a, r):
  if r.baseline is undefined: return (null, false)            # 勝手な baseline を作らない
  if r.operator==">=":
     if not (r.baseline < r.target): return (null, true)      # INVALID_BASELINE
     return (clamp((a - r.baseline)/(r.target - r.baseline), 0, 1), false)
  if r.operator=="<=":
     if not (r.baseline > r.target): return (null, true)      # INVALID_BASELINE
     return (clamp((r.baseline - a)/(r.baseline - r.target), 0, 1), false)
```
- baseline 無し → `progress_fraction=null`（state は met/unmet のみ、partial は出さない）。
- 例：現状60→目標80、実測65、baseline=60 → 0.25（65/80=0.81 の誤認を回避）。

### 5-4. `latest` の measured_at
`latest` は `measured_at` のある測定値のみ対象。全 null → indeterminate（`NO_MEASURED_DATE`）。`created_at` にフォールバックしない。同一 `measured_at` の時だけ tie-break に `created_at`/`id`。

### 5-5. `count` は PP 単位で distinct（追加⑥）
1つの Proof Point が条件を満たす測定値を複数持っても、**count では PP を1件**として数える（`COUNT(DISTINCT proof_point_id)`）。1回の調査の複数行が複数実績に化けるのを防ぐ。

## 6. 人間判断の優先・失効条件（追加①②）

### 6-1. 有効性判定（失効・再確認）
`currentValidHumanJudgment(DE)`：
- `is_current` の判断 h を取得（なければ null）。
- **manual_review**：次の人間レビューまで有効（`valid_until` があればそれも尊重）。ただし DE の `rule.type` が manual 以外に変わっていれば「再レビュー要」info を発火（自動評価に委ねるかは人間が判断）。
- **automatic_override**：以下を**両方満たす時だけ有効**。
  - `rule_hash == hash(現在の achievement_rule)`（ルール不変）
  - `現在の evidence_data_updated_at <= h.evidence_data_updated_at`（評価後に関連PP・測定値・verifies が更新されていない）
  - どちらか崩れたら override は**失効**。h を使わず自動評価にフォールバックし、「自動override後にデータ/ルールが変わりました。再確認してください」info を発火（レコードは残し、再確認を促す）。

**原則:** `manual_review`＝次の人間レビューまで有効／`automatic_override`＝rule・判定データ変更で再確認が必要。**人間判断が永久に自動判定を無効化しない。**

### 6-2. 現行1件のDB制約
§2-3 の部分ユニークインデックスで `is_current=true` を DE ごと1件に限定。登録は「旧→false／新→true」を同一トランザクションで。

### 6-3. manual_review と automatic_override の分離
- **manual_review**：`rule.type="manual"` の DE を人が達成判断（正規フロー）。
- **automatic_override**：自動評価を例外的に修正（失効あり）。
- 監査上・運用上、両者を混同しない。理由 `reason` は両方**必須**。

### 6-4. 手動 state と progress の整合（追加⑦）
`desired_evidence_evaluations` に次の CHECK（またはアプリ検証）：
```
state=met            → progress_fraction ∈ {1, null}
state=unmet          → progress_fraction ∈ {0, null}
state=partially_met  → 0 < progress_fraction < 1  もしくは null
state=indeterminate  → 人間評価では選択不可（indeterminate は自動エンジンのみ）
```
`met + 0.4` のような矛盾入力を許可しない。「判断できない」を残したい場合は評価を作らない（＝エンジンが indeterminate 表示）か、`reason` に明記。

## 7. 実証進捗と判定可能率（追加④）

vision が `requires` する DE 群で集計。`execution_state='cancelled'` は分母から除外。**進捗と判定可能率は必ずセットで表示**（進捗単独表示は禁止）。

```
evaluable = state ∈ {unmet, partially_met, met}（indeterminate を除外）
各DEの寄与 = progress_fraction があればそれ、無ければ (state==met ? 1 : 0)

実証進捗 = Σ_evaluable ( weight × 寄与 ) / Σ_evaluable ( weight )

判定可能率（重み）= Σ_evaluable ( weight ) / Σ_非cancelled ( weight )      # ← 重み付き（追加④）
判定可能率（件数・補助）= evaluable件数 / 非cancelled件数
```
**表示例（3値必須）:**
```
実証進捗：72%
判定可能範囲：重み換算 75%
判定可能件数：6/8 件
```
- 重要度4.0のDEが判定不能で0.25のDEだけ判定可能、のような偏りを「件数7/8」で誤魔化さない（重み換算で低く出る）。
- 「重要DEの大半が判定不能・可能な1件だけ達成」の場合、実証進捗100%／判定可能範囲10% と**必ず並記**して過大評価を防ぐ。

## 8. 状態遷移

**Desired Evidence 実行状態（手動）:** `planned → in_progress ⇄ paused`／任意で `cancelled`（分母除外）。
**Desired Evidence 達成状態（動的）:** `unmet ↔ partially_met ↔ met`（実績・rule で再計算・後戻り可）／算出不能は `indeterminate`。
**Value Proposition ライフサイクル:** `target → transition_candidate → current → retired`。**DEが met でも自動で current にしない**。`transition_candidate`（昇格待ち）で止め、管理者レビューで current 昇格（単発実績≠恒常価値）。却下は target へ差し戻し。

## 9. FACT / ASPIRATION の AI注入

| ブロック | 引用/断定 | 中身 |
|---|---|---|
| **FACT**（引用可） | 可 | `proof_points`（＋その測定値・metric_label/value/measured_at）＋ `value_propositions` の `lifecycle_state='current'` |
| **ASPIRATION**（断定・引用禁止） | 不可（「目指す/これから」のみ） | `lifecycle_state ∈ {target, transition_candidate}` の提供価値 ＋ `desired_evidence`（未達/一部）＋ vision |

- `transition_candidate` は保守的に **ASPIRATION**（昇格して current になるまで事実断定しない）。
- `desired_evidence` が met でも、引用できるのは**紐づく Proof Point（＋測定値＝事実）**であって DE 自体ではない。
- 実装は `lib/copy/ontology-blocks.ts` に ASPIRATION ブロックを追加。0件はフォールバックで挙動不変。

| 名称 | 重大度 | 条件 |

## 13. 加算マイグレーション順序（dual-run・既定値で挙動不変）

過去の理念オントロジー移行と同じ作法（ローカル.sql先行→適用→`schema_migrations` 記録一致→`NOTIFY pgrst reload`・破壊的変更なし）。

1. **`desired_evidence` 作成**（RLS・FK index・全既定値）＋ElementKind／端点検証トリガに `desired_evidence` 追加。→ 空テーブルで挙動不変。
2. **`proof_point_measurements` 作成**（RLS・FK index）。→ 空で不変。
3. **`desired_evidence_evaluations` 作成**（RLS・FK index・**部分ユニーク `WHERE is_current=true`**）。→ 空で不変。
4. **`value_propositions.lifecycle_state`（default current）＋ promoted_by/at 追加**。NOTIFY reload。→ 既存VPは current。
5. **`element_relations.relation_type` に aspiresTo/requires/toBeEvidencedBy/verifies 追加**（enum/CHECK拡張・既存不変）。
6. **判定エンジン実装**（`lib/brand/` に evaluate＝§5・失効判定＝§6・rule検証＝§3-3・進捗＝§7。read専用・非保存）。
7. **整合性チェック更新**（`lib/brand/integrity.ts`：既1を current-scoped、新 info 追加）。
8. **コピーAI FACT/ASPIRATION 分離**（`lib/copy/ontology-blocks.ts`・0件フォールバックで不変）。
9. **superadmin UI**（§11）。
10. **ID INC. で1本通し検証**：vision→requires→DE（rule＋重み）→測定値付き Proof Point→verifies→state/progress/判定可能率、および target 提供価値→transition_candidate→昇格レビュー→current。コピー/整合性の before/after。
11. 問題なければ本番反映（1〜5のDB先行、6〜9のコード後追いでも後方互換）。

各段は単独で安全（前段が無くても既定値で従来動作／データ0件でフォールバック）。

## 14. DB実装確定事項（v1.1・SQL化前の追補）

設計の根本変更ではなく、DB実装時の曖昧さを消す確定事項。以下は本仕様の一部（§2・§6・§7・§13 を上書き補足）。

### 14.1 override 失効は「evidence バージョン」で厳密化
- `desired_evidence` に **`evidence_updated_at timestamptz not null default now()`** を追加。
- 次の変更で**トリガが対象DEの `evidence_updated_at` を `now()` に更新**：`verifies` 関係の追加/削除、関連 `proof_points` の更新、関連 `proof_point_measurements` の追加/更新/削除。
- `desired_evidence_evaluations` は評価時点のスナップショットを保持：**`rule_hash`**（評価時 rule）＋ **`evidence_version_at_eval timestamptz`**（＝評価時の `DE.evidence_updated_at`）。※§2-3 の旧 `evidence_data_updated_at` は本項に置換。
- `automatic_override` の有効条件：`rule_hash == 現在rule_hash` かつ `evidence_version_at_eval == 現在 DE.evidence_updated_at` かつ（`valid_until` null または now<valid_until）。**削除もトリガの bump で検知**できる（ライブ行の MAX 方式は削除を見逃すため不採用）。

### 14.2 `rule_hash` はDB側で正規化ハッシュ（生成主体を一つに）
- jsonb はキー順を正規化保存するため、`encode(digest(achievement_rule::text,'sha256'),'hex')`（pgcrypto）を**DB側で算出**。評価レコード作成時に同一トランザクションでDBが付与。**アプリ側では作らない**（生成差異の防止）。

### 14.3 company 整合を複合FKで担保
- `proof_points` に `UNIQUE(company_id, id)`、`desired_evidence` に `UNIQUE(company_id, id)` を付与。
- `proof_point_measurements`：`FOREIGN KEY(company_id, proof_point_id) REFERENCES proof_points(company_id, id)`。
- `desired_evidence_evaluations`：`FOREIGN KEY(company_id, desired_evidence_id) REFERENCES desired_evidence(company_id, id)`。
- `element_relations` は既存の端点検証トリガで同一company担保（`desired_evidence` kind もこの検証に追加）。

### 14.4 `is_current` ≠ `is_valid`
- `is_current` ＝ **最新の人間判断**（失効しても true のまま）。部分ユニークは `is_current` に付ける。
- `is_valid` ＝ **動的算出**（rule_hash・evidence_version・valid_until）。**保存しない**。
- 失効した override は `is_current=true` のまま／`is_valid=false` → エンジンは自動判定へフォールバック。UI表示「最新の人間判断あり／現在失効中／自動判定を使用」。**`is_current` を自動で false にしない**（最新判断が辿れなくなるため）。

### 14.5 `aspiresTo` の許容端点（明示）
- `source_kind ∈ {value_proposition, philosophy_element}`／`target_kind ∈ {philosophy_element}`（target の philosophy type = `vision`）。端点検証で担保。
- 初期UIは「**target 提供価値 → vision**」のみ提供。philosophy 間 aspiresTo は非表示。

### 14.6 進捗のゼロ分母
- 非cancelled DE が0件、または evaluable の重み合計が0 のとき：**実証進捗 = null／判定可能率 = 0／表示「獲得目標が未設定」**。0%表示にしない（「設定済みだが未達」との誤認防止）。

### 14.7 実装フェーズ順（DB→ドメイン→利用／コピーAIとUIは独立デプロイ）
- **DBフェーズ**：1 `desired_evidence` ／ 2 `proof_point_measurements` ／ 3 `desired_evidence_evaluations` ／ 4 VP列 ／ 5 relation enum・端点トリガ拡張。
- **ドメインロジックフェーズ**：6 rule validator ／ 7 evaluation engine ／ 8 human判断 validity evaluator ／ 9 progress & coverage calculator ／ 10 integrity checks。
- **利用フェーズ**：11 superadmin UI ／ 12 FACT/ASPIRATION連携 ／ 13 ID INC. 検証。**UIを先に**（正しいデータが作れる状態を確認してから）、**コピーAIは後**。両者は**独立デプロイ可能**にする。
