# ブランドオントロジー 判定ロジック詳細 v2（測定値テーブル化・state/progress分離・indeterminate）

**作成日:** 2026-07-18
**位置づけ:** 判定ロジック詳細 v1 への9点修正を反映した確定版。これを C案詳細設計 v1 の §2（proof_points / desired_evidence）・§6（進捗）へ統合したうえで、加算マイグレーションへ進む。**コード変更はしない。**

**v1からの修正（9点）:**
1. Proof Point の測定値を**別テーブル `proof_point_measurements`**へ（1実績＝複数測定値を許容）。
2. 判定は単位だけでなく **`metric_key`＋単位**で抽出（同単位・別指標の混入を防止）。
3. **達成状態（state）と進捗率（progress_fraction）を分離**（構造化した判定結果を返す）。
4. **`indeterminate`（判定不能）を追加**（未達と区別）。
5. **baseline の自動補完を廃止**（無ければ progress は出さない）。
6. **manual review ≠ automatic override** を概念分離（監査を分ける）。
7. **`partially_met = 0.5` 固定を廃止**（手動は state と progress を個別指定＋理由）。
8. **`latest` の `measured_at` null 規則**を明文化（created_at にフォールバックしない）。
9. **演算子を `>=` `<=` に限定**（厳密比較の state/progress 矛盾を回避）＋ rule 語彙を明示語に。

---

## 1. データ構造（確定）

### 1-1. `proof_point_measurements`（新規・測定値テーブル）

1つの Proof Point（事実）から複数の測定値が出る（例：1回の顧客調査から 認知率72% / 第一想起18% / 推奨意向65%）。よって測定値は別テーブル。

| カラム | 型 | 既定 | 説明 |
|---|---|---|---|
| `id` | uuid PK | gen | |
| `company_id` | uuid FK | — | RLS/所属（**FK index必須**） |
| `proof_point_id` | uuid FK→proof_points | — | どの事実の測定値か（**FK index必須**） |
| `metric_key` | text | — | **内部識別子**（例 `brand_awareness_rate`）。判定の一致キー。表記揺れを防ぐ正規語彙 |
| `metric_label` | text | '' | 人間向け表示名（例「ブランド認知率」）。判定には使わない |
| `metric_value` | numeric | — | 測定値（例 72） |
| `metric_unit` | text | — | 単位（例 `%`）。**metric_key とセットで一致判定** |
| `measured_at` | date | null | 測定日（調査実施日等）。`latest` 集計・鮮度に使用。**登録日ではない** |
| `measurement_scope` | text | '' | 母集団・対象範囲（例「全国20-40代」「既存顧客」）。同一 metric_key を別母集団で測る混同を防ぐ（C案は表示・監査用。scope一致判定は B案拡張） |
| `source_reference` | text | '' | 出典（調査レポートURL・資料名等）。真正性確認の根拠 |
| `created_at` / `updated_at` | timestamptz | now | |

- 定性的な実績（数値の無い事例）は測定値行を持たない＝ `count`/`boolean` には効くが `aggregate` の対象にはならない。
- `metric_key` は**会社内で正規化された語彙**として運用（同義の別表記を作らない）。管理UIは既存 metric_key をサジェストする。

### 1-2. `desired_evidence`（v1から修正）

| カラム | 型 | 既定 | 説明 |
|---|---|---|---|
| `id` / `company_id` / `title` / `description` / `importance_weight` / `execution_state` / `sort_order` / timestamps | （C案詳細設計 v1 のまま） | | 実行状態＝手動：planned/in_progress/paused/cancelled |
| `achievement_rule` | jsonb | `{}` | **判定の単一の正**（§2）。目標値・単位・metric_key・集計・演算子を内包 |
| `verification_method` | text | '' | **人間用**：各実績が本物かをどう確かめるか（自動判定は achievement_rule 専任） |
| ~~`target_value` / `target_unit`~~ | — | — | **廃止**（achievement_rule に集約） |

達成状態・進捗率は**カラムに持たない**（動的算出＝§4）。手動判断は §1-3 のテーブルへ。

### 1-3. `desired_evidence_evaluations`（新規・人間判断の記録／推奨）

自動評価は保存しない（常に動的）。**保存するのは「人間が下した判断」だけ**。manual review と automatic override を `evaluation_source` で区別して監査可能にする。

| カラム | 型 | 説明 |
|---|---|---|
| `id` / `company_id` | uuid | |
| `desired_evidence_id` | uuid FK | 対象DE（FK index） |
| `evaluation_source` | text(enum) | `manual_review`（rule=manual の正規フロー）/ `automatic_override`（自動結果の例外修正） |
| `achievement_state` | text(enum) | unmet / partially_met / met（人が指定） |
| `progress_fraction` | numeric | null | **state とは別に**指定（0.5固定にしない。例 0.7）。null可 |
| `evaluated_by` | uuid | 実施者（admin_users/auth） |
| `evaluated_at` | timestamptz | |
| `reason` | text | **理由必須** |
| `is_current` | boolean | 最新の有効判断か（履歴を残しつつ現行1件を特定） |

> **軽量代替:** テーブルを増やしたくない場合は `desired_evidence` に `reviewed_*`（manual review用）と `override_*`（automatic override用）の2系統カラムを持たせる形でもよい。ただし**概念（正規の人間判断 vs 自動結果の修正）は必ず分ける**。履歴・監査の観点からは本テーブルを推奨。

### 1-4. `verifies` は「立証根拠の採用」関係（意味の明文化）

`verifies`（proof_point → desired_evidence）は単なる関連付けではなく、**「この実績を、この獲得目標の立証根拠として管理者が採用する」**行為。関係の作成＝管理者承認とみなす（C案の簡略化）。これにより `boolean`（存在で met）にも「誤紐付けで即metにならない」意味が生まれる。

- **将来（B案）拡張:** 関係自体に `verification_status` / `verified_by` / `verified_at` / `verification_note` を持たせ、採用を二段階承認にできる。C案では関係作成＝採用。

### 1-5. 最終データ構造（俯瞰）

```
Desired Evidence
├─ achievement_rule        （機械判定条件・単一の正）
├─ verification_method     （人間の真正性確認）
├─ importance_weight       （進捗の重み）
└─ execution_state         （planned/in_progress/paused/cancelled）

Proof Point ──< Proof Point Measurement
                 ├─ metric_key / metric_label
                 ├─ metric_value / metric_unit
                 ├─ measured_at / measurement_scope / source_reference

Proof Point ──verifies──> Desired Evidence    （管理者が立証根拠として採用）

Desired Evidence ──< Desired Evidence Evaluation   （人間判断のみ記録）
                      ├─ evaluation_source（manual_review / automatic_override）
                      ├─ achievement_state / progress_fraction
                      └─ evaluated_by / evaluated_at / reason

Evaluation（動的算出・非保存）→ AchievementEvaluation
```

## 2. `achievement_rule` スキーマ v1（明示語彙・演算子 `>=`/`<=` 限定）

```ts
type AchievementRuleV1 =
  | { version: 1; type: "boolean"; minimum_proof_count?: number }
  | { version: 1; type: "count";
      threshold: number;
      metric_filter?: { metric_key: string; unit?: string; operator?: ">=" | "<="; value?: number } }
  | { version: 1; type: "aggregate";
      metric_key: string;
      aggregation: "sum" | "average" | "maximum" | "minimum" | "latest";
      unit: string;
      operator: ">=" | "<=";
      target: number;
      baseline?: number }
  | { version: 1; type: "manual" };
```

- 略語廃止（`aggregation`/`operator`/`average`/`maximum`/`minimum`）＝長期保守で誤読を減らす。
- **演算子は `>=` と `<=` のみ**。ブランドKPIは通常これで十分。厳密 `>` `<` を入れると「target ちょうどで met=false なのに progress=1」という矛盾が出るため、初期実装から除外。
- `aggregate` は `metric_key` **必須**（同単位・別指標の混入防止）。
- `baseline` は**任意**。無ければ progress は出さない（§4-3）。
- 例（現状60%→目標80%、最新値で判定）:
```json
{ "version":1, "type":"aggregate", "metric_key":"brand_awareness_rate",
  "aggregation":"latest", "unit":"%", "operator":">=", "target":80, "baseline":55 }
```

## 3. 判定結果の構造（state と progress を分離）

```ts
type AchievementEvaluation = {
  state: "unmet" | "partially_met" | "met" | "indeterminate";
  progress_fraction: number | null;      // 0〜1。baseline無し等では null
  source: "automatic" | "manual";
  evaluated_value: number | null;        // aggregate の集計結果など（監査・表示用）
  matched_measurement_count: number;     // 判定に使えた測定値/実績の件数
  reason_code: string;                   // 下表
};
```

**state（達成したか）＝演算子×目標での判定。progress_fraction（どこまで来たか）＝baseline→target の進捗表示。両者は別物。** `>=`/`<=` 限定により両者は境界でも矛盾しない。

reason_code（例）: `MET` / `BELOW_TARGET` / `INSUFFICIENT_COUNT` / `NO_MATCHING_MEASUREMENT` / `NO_MEASURED_DATE` / `INVALID_RULE` / `MANUAL_REVIEW` / `MANUAL_OVERRIDE`。

## 4. 判定アルゴリズム

```
function evaluate(DE) -> AchievementEvaluation:

  # 0) 人間判断が現行で存在すれば最優先（manual review / automatic override）
  e = latest desired_evidence_evaluations where is_current
  if e exists:
     return { state:e.achievement_state, progress_fraction:e.progress_fraction,
              source:"manual", evaluated_value:null,
              matched_measurement_count:0,
              reason_code: e.evaluation_source=="manual_review" ? "MANUAL_REVIEW" : "MANUAL_OVERRIDE" }

  P = proofsAdoptedVia_verifies(DE)         # 端点解決済みのみ
  r = DE.achievement_rule
  if r is empty or invalid:
     return { state:"indeterminate", progress_fraction:null, source:"automatic",
              evaluated_value:null, matched_measurement_count:0, reason_code:"INVALID_RULE" }

  switch r.type:

    "boolean":
        n = |P| ; need = r.minimum_proof_count ?? 1
        state = n >= need ? "met" : "unmet"
        return { state, progress_fraction: state=="met"?1:0, source:"automatic",
                 evaluated_value:n, matched_measurement_count:n,
                 reason_code: state=="met"?"MET":"INSUFFICIENT_COUNT" }

    "count":
        # metric_filter があれば、その key/unit/operator/value を満たす測定値を持つ P に限定
        Pf = filterProofsByMeasurement(P, r.metric_filter)
        n = |Pf|
        state = n >= r.threshold ? "met" : (n>0 ? "partially_met" : "unmet")
        frac = clamp(n / r.threshold, 0, 1)          # count は threshold が起点=0 から明確
        return { state, progress_fraction:frac, source:"automatic",
                 evaluated_value:n, matched_measurement_count:n,
                 reason_code: state=="met"?"MET":"INSUFFICIENT_COUNT" }

    "aggregate":
        M = measurements(P) where metric_key==r.metric_key AND metric_unit==r.unit AND metric_value!=null
        if r.aggregation=="latest": M = M where measured_at != null      # §4-4
        if M is empty:
            reason = (r.aggregation=="latest") ? "NO_MEASURED_DATE" : "NO_MATCHING_MEASUREMENT"
            return { state:"indeterminate", progress_fraction:null, source:"automatic",
                     evaluated_value:null, matched_measurement_count:0, reason_code:reason }
        a = aggregate(M, r.aggregation)              # sum/average/maximum/minimum/latest(measured_at最新)
        met = (r.operator==">=") ? a>=r.target : a<=r.target
        frac = progressFraction(a, r)                # §4-3（baseline無ければ null）
        state = met ? "met" : (frac!=null && frac>0 ? "partially_met" : "unmet")
        return { state, progress_fraction:frac, source:"automatic",
                 evaluated_value:a, matched_measurement_count:|M|,
                 reason_code: met?"MET":"BELOW_TARGET" }

    "manual":
        # 人間判断が無い manual は判定不能（未達ではない）
        return { state:"indeterminate", progress_fraction:null, source:"automatic",
                 evaluated_value:null, matched_measurement_count:0, reason_code:"MANUAL_REVIEW" }
```

### 4-1. 単位安全＋metric_key 安全（#2）
`aggregate` の集計対象は **`metric_key==rule.metric_key` かつ `metric_unit==rule.unit`** を両方満たす測定値のみ。片方でも違えば除外。除外が発生し、かつ対象が空になれば `indeterminate`（`NO_MATCHING_MEASUREMENT`）。単位は同じでも別指標（認知率と解約率がともに%）は metric_key で弾かれる。

### 4-2. indeterminate と unmet の区別（#4/#9）
- **unmet** … 測れた。しかし足りない（例：件数0、集計値が目標未満）。
- **indeterminate** … 測れない（測定値なし／key・単位不一致で対象空／rule不正／latestで測定日なし）。
- 「実績が足りない」のか「データが足りない」のかを混同しない。

### 4-3. progressFraction（baseline 自動補完しない・#5）
```
progressFraction(a, r):
  if r.baseline is undefined: return null          # 勝手な baseline を作らない
  if r.operator == ">=":                            # 高いほど良い
      if target == baseline: return a>=target ? 1 : 0
      return clamp((a - baseline)/(target - baseline), 0, 1)
  if r.operator == "<=":                            # 低いほど良い（baseline>target 前提）
      if baseline == target: return a<=target ? 1 : 0
      return clamp((baseline - a)/(baseline - target), 0, 1)
```
- baseline 無し → `progress_fraction = null`（state は met/unmet のみ・partial は出さない）。
- 例：現状60→目標80、実測65、baseline=60 → (65-60)/(80-60)=**0.25**（"半分" 誤認だった 65/80=0.81 を回避）。
- 目標0や 2×target の恣意的既定は**作らない**（0除算・実態乖離を防ぐ）。

### 4-4. `latest` の measured_at null（#8）
- `latest` は **`measured_at` のある測定値だけ**を対象に最新を採る。
- 全て null → `indeterminate`（`NO_MEASURED_DATE`）。`created_at` へフォールバックしない（登録日≠測定日。古い調査を後から登録→最新誤認を防ぐ）。
- 同一 `measured_at` の時だけ、安定ソート目的で `created_at`/`id` を tie-break に使う。

## 5. 手動判断（manual review と override の分離・#6/#7）

| 種別 | いつ | 記録 | progress |
|---|---|---|---|
| **manual review** | `type:"manual"` の DE を人が達成判断（正規フロー） | `desired_evidence_evaluations`（source=`manual_review`） | state と progress_fraction を**個別指定**（例 partially_met / 0.7）＋理由必須 |
| **automatic override** | 自動評価を例外的に修正 | 同テーブル（source=`automatic_override`） | 同上・理由必須 |

- **`partially_met=0.5` 固定は廃止**。手動は state と progress を別々に入れる（推奨：Bパターン）。理由記録は必須。
- どちらも `is_current` で現行1件を特定し、履歴を残す（誰がいつなぜ、を監査可能）。

## 6. 実証進捗への集約（indeterminate の扱い・#9）

vision が `requires` する DE 群で重み付き集計。`execution_state='cancelled'` は分母から除外。

- **推奨：indeterminate は分子・分母の両方から除外**し、別途「判定可能率（coverage）」を併記。
```
実証進捗 = Σ_evaluable ( weight × progress_or_state ) / Σ_evaluable ( weight )
   evaluable = state ∈ {unmet, partially_met, met}（indeterminate を除く）
   各DEの寄与 = progress_fraction があればそれ、無ければ (met?1:0)
判定可能率 = evaluable 件数 / (全DE − cancelled) 件数
```
- 表示例：**「実証進捗 72%（判定可能な獲得目標 6/8）」**。残り2件は「判定不能」を明示（データ不足を可視化）。
- **簡易フォールバック:** indeterminate を分母に含め寄与0として扱い、UIで「判定不能」を明示するだけでもよい（初期実装可）。ただし coverage 併記の方が「実績不足」と「データ不足」を混同しない。

## 7. 具体例

**例A 複数測定値・latest（#1/#2/#8）**
- Proof Point「2026年度ブランド調査」→ measurements: `brand_awareness_rate=72%`, `first_recall_rate=18%`, `recommendation_intent=65%`（全て measured_at=2026-05-01）。
- DE「ブランド認知率80%以上」 rule=`{aggregate, metric_key:"brand_awareness_rate", aggregation:"latest", unit:"%", operator:">=", target:80, baseline:55}`。
- 集計＝認知率のみ抽出（他指標・別keyは除外）。latest=72。met? 72>=80→false。progress=(72-55)/(80-55)=0.68 → **partially_met / 0.68 / value=72**。解約率(%)が別DEにあっても混ざらない。

**例B 件数（#2）**
- DE「+10pt以上のスコア改善事例3件」 rule=`{count, threshold:3, metric_filter:{metric_key:"brand_score_delta", unit:"pt", operator:">=", value:10}}`。
- 該当測定値を持つ実績が2件 → partially_met / 0.67 / matched=2。

**例C 判定不能（#4）**
- DE「平均改善+15pt以上」だが verifies 実績に pt の測定値が1つも無い → **indeterminate / null / NO_MATCHING_MEASUREMENT**（unmet にしない）。UIは「データ不足で判定不能」。

**例D 手動（#5/#6/#7）**
- DE「第一想起の獲得」 rule=`{manual}`。レビューで partially_met / progress 0.4 / 理由「主要媒体2件で第一想起として言及。残るは横展開」/ evaluated_by 記録。

## 8. C案詳細設計 v1 への統合差分（この後の作業）

| 対象 | v1 | v2（本書で確定） |
|---|---|---|
| Proof Point 測定値 | proof_points に4カラム | **別テーブル `proof_point_measurements`**（1実績＝複数測定・metric_key） |
| 判定の一致条件 | 単位のみ | **metric_key＋単位** |
| DE の目標値 | target_value/unit カラム | achievement_rule に集約（カラム廃止） |
| 判定結果 | 単一 frac | **AchievementEvaluation 構造**（state / progress_fraction / evaluated_value / matched_count / reason_code） |
| 状態語彙 | met/partial/unmet | **＋ indeterminate** |
| baseline | 未設定は 2×target/0 補完 | **補完しない**（無ければ progress=null） |
| 演算子 | >,>=,<,<= | **>=, <= のみ** |
| 手動 | override（0.5固定） | **manual_review と override を分離**・state/progress 個別・理由必須 |
| latest | created_at フォールバック | **measured_at 必須・null は indeterminate** |
| 進捗集計 | 全DE平均 | **indeterminate 除外＋判定可能率併記** |

**C案の新規テーブルは3つになる**：`desired_evidence` / `proof_point_measurements` / `desired_evidence_evaluations`。いずれも判定の正確性・監査に必要な最小限で、B案固有の `desired_brand_states`・`milestones` は引き続き据え置き（＝スコープ肥大ではない）。
