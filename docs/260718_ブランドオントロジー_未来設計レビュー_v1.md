# ブランドオントロジー 未来設計レビュー v1

**作成日:** 2026-07-18
**目的:** 現在のブランドオントロジー（AIが企業ブランドを理解・推論するための知識モデル）が「現状を記述するモデル」に寄っていないかを、実装コード・データ構造に接地して診断し、「未来を設計するモデル」へ寄せる場合の変更案・影響範囲・移行を提示する。
**読み方:** まず「1. 一言で」と「2. 現状の設計思想」を読めば全体像がつかめます。技術判断は 5〜7、経営判断は 4 と 8 を見てください。

---

## 1. 一言で

いまのオントロジーは、**「うちは何者か・それを証拠で裏づけられるか」を正しく整理する、履歴書＋証明書のような作り**になっている。信頼性・一貫性・ウソ（盛り）防止には強い。
一方でブランディングの本質は **「理想の未来へ組織を導く」**こと。今のモデルには **「まだ証明できていないが、これから目指す姿」を一級の情報として置く場所が無い**。

結論：**記述型を捨てるのではなく、未来の層を足して二階建てにする。** 現在（証拠つき）＋目標（理想）＋その差分（何を証明すれば到達できるか）を持たせる。反捏造（願望をウソにしない）の仕組みは維持する。

---

## 2. 現状の設計思想の要約

現在のオントロジーは5種類の「要素」と、それらを結ぶ「関係」でできている。

**要素（5種）**
- 理念（`philosophy_elements`）＝ ミッション / ビジョン / バリュー / 行動指針 / 事業内容
- 提供価値（`value_propositions`）＝ 顧客への約束
- 実績・エピソード（`proof_points`）＝ 約束を裏づける事実
- 表現ルール（`governance_rules`）＝ 言ってよい／避ける、トーンの禁則
- ペルソナ（`brand_personas`）＝ 顧客像

**関係（6種）** `guides`（方向づける）/ `evidencedBy`（裏づけられる）/ `promisedTo`（約束する相手）/ `communicatedAs`（表現される）/ `constrainedBy`（制約される）/ `conflictsWith`（矛盾しうる）

**貫かれている思想（良い点）**
- **事実は機械・語りはAI**：数値や引用の裏取りはコードで判定し、AIには創作させない。
- **証拠に接地する**：約束（提供価値）は実績（proof_point）で裏づける。コピーAIも「引用してよいのは proof_point だけ・捏造禁止」。
- **一貫性を点検する**：整合性チェックで「約束はあるが証拠がない」「理念から線が繋がっていない孤島」などを検出する。

この設計は **「盛っただけの・中身のないブランド」を構造的に防ぐ**ために作り込まれてきた。ここは大きな資産で、壊してはいけない。

## 3. どこが「現状記述型」になっているか（コード接地の指摘）

「未来に弱い」と言えるのは、感覚ではなく **実装がそうなっている**から。具体的に3点。

**(1) 約束は「すでに証明できること」に縛られている**
整合性チェックの筆頭が「**裏づけのない約束**」（`lib/brand/integrity.ts` チェック1）。提供価値（約束）は実績（＝過去の`proof_point`）で裏づけよ、というルール。
→ 裏を返すと **「今はまだ証明できないが、これから実現する約束」は"綻び（warn）"として叱られる**。これは未来志向の宣言を抑制する方向に働く。ビジョン型ブランディングと相性が悪い。

**(2) 「実績＝過去」しか証拠として持てない**
`proof_point` は種別（`source_type`）を持つが、いずれも **すでに起きたこと（実績・エピソード）**。ラベルも「実績・エピソード」。
→ **「これから獲得する予定の証拠」「約束を果たすための計画」を置く場所が無い。** 証拠は後ろ向き（バックミラー）専用。

**(3) 関係の型が全部「現在形の構造」**
6つの関係（guides / evidencedBy / promisedTo / …）は **すべて "いま A と B がどういう構造で結ばれているか"** を表す。`relations.ts` の自然文も「A は B を方向づける」「A は B に裏づけられる」と全部現在形。
→ **「A は将来 B を目指す」「A と B の間にはギャップがある」「B は C を達成すれば手に入る」といった"時間・到達・差分"の関係が一つも無い。**

**(4) 整合性の"根"が現在の体系の内部完結**
「**理念から辿れない要素**」チェック（同ファイル チェック7）は、全要素がミッション/ビジョンから線で辿れることを求める＝**今ある体系が内部で閉じて矛盾しないか**を見る。これは大事だが、視線は「現状システムの自己整合」に向いていて、「現状と理想のギャップ」には向いていない。

**補足（フェアに言うと）：完全な現状記述ではない。** ビジョン（`vision`）は本来"目指す姿"で、未来要素は存在する。問題は **ビジョンが他の要素と"未来の関係"で結ばれていない**こと。ビジョンはあるのに、そこへ至る道（提供価値→実績→計画）が現在形の裏取りロジックに飲み込まれ、単なる"今の看板"として扱われている。**未来が一級市民になっていない**、が正確な言い方。

## 4. 未来設計型へ：変えるべき方向（統合案）

二者択一（記述 or 設計）ではなく、**現在・目標・道のりの三層に拡張**する。経営の言葉で言うと「現在地／目的地／道のり」を全部モデルに持たせる。

- **現在地（今の姿・証拠つき）** … 今のロジックそのまま。信頼性の土台。
- **目的地（目指す姿・理想）** … ビジョンを頂点に、"まだ証明できないが目指す提供価値・ポジション"を一級要素として置く。
- **道のり（差分と計画）** … 現在地と目的地の**ギャップ**、および**それを埋めるために獲得すべき証拠・マイルストーン**。

キモは **「目標」と「ウソ」を取り違えない仕組み**を同時に入れること。具体的には各要素・約束に **時制タグ（現有 / 目標 / 移行中）** を付け、**"目標"タグの付いた約束はコピーAIが決して"証明済みの事実"として断定引用できない**ようにする（表現は「目指す」「これから」に限定）。これで未来を扱っても捏造にはならない。

### 変更の候補（概念・関係・データ構造）

**A. 要素に「時制（stance）」を持たせる**
`value_propositions` と `proof_points`（と必要なら `philosophy_elements`）に `time_stance`（`current`＝現有 / `target`＝目標 / `in_progress`＝移行中）を追加。既定は `current`（＝既存データは今までどおり＝後方互換）。

**B. 未来向けの関係型を足す**
既存6種に加えて時間・到達の関係を追加。例：
- `aspiresTo`（A〈現状〉は B〈目標〉を目指す）
- `earnedBy`（B〈未来の約束〉は C〈獲得予定の証拠／達成条件〉で手に入る）
- `milestoneOf`（C は目標 B の中間地点）
- （任意）`gapWith`（A と B の間にギャップがある＝道のりの明示）

**C. 「約束」を現在と未来で扱い分ける**
提供価値に時制が付くことで、整合性チェックを次のように賢くする：
- `current` の約束に証拠が無い → 今までどおり「裏づけのない約束」でwarn（信頼性を守る）。
- `target` の約束に証拠が無い → **叱らない。**代わりに「**この未来の約束には獲得計画（earnedBy）が未登録**」を促す（＝道のりを描かせる）。

## 5. Proof Point の判断（残す / 役割変更 / 分割）

**結論：残す。ただし役割を「後ろ向きの門番」から「前向きのロードマップも兼ねる台帳」へ広げる。**

- **削除はしない。** 現有の実績は信頼性の生命線で、コピーAIの唯一の引用元。ここを外すと反捏造が崩れる。
- **役割転換＋軽い分割**：`proof_point` に状態を持たせる（例 `proof_status = proven`〈現有〉/ `planned`〈獲得予定〉）。
  - `proven`：今までどおり。約束を裏づけ、コピーで引用可。
  - `planned`：まだ起きていない"獲得予定の証拠・達成条件"。**未来の約束（target）に `earnedBy` で紐づく道標**。コピーでは**事実として引用禁止**（計画としてのみ扱う）。
- これで proof_point は「**何を証明済みか（現在）**」と「**何を証明すれば理想に届くか（未来）**」の両方を持つ台帳になる。テーブル増設ではなく**状態カラム1本で足りる**のが利点。

## 6. 影響範囲と移行案（壊さず足す）

すべて **加算的（additive）＝既定値で従来挙動を維持** できる設計にする。

**DB（マイグレーション・すべて既定値あり）**
- `value_propositions.time_stance`（default `current`）
- `proof_points.proof_status`（default `proven`）
- `element_relations.relation_type` に `aspiresTo` / `earnedBy` / `milestoneOf`（enum拡張・既存行は不変）
- （必要時）`philosophy_elements.time_stance`

**コードの影響**
- **整合性チェック（`lib/brand/integrity.ts`）**：チェック1を時制で分岐（`current`のみwarn、`target`は"計画未登録"info）。新チェック「未来の約束に earnedBy が無い」を追加。→ 変更は1ファイルに集約。
- **関係の要約注入（`lib/brand/relations.ts`）**：新関係型の自然文（「A は B を目指す」「B は C で手に入る」）を PHRASE に追加。
- **コピーAI（`lib/copy/ontology-blocks.ts`）**：`proven` 実績と `current` 約束＝FACT（引用可）、`target` 約束・`planned` 証拠＝ASPIRATION（"目指す"としてのみ・断定引用禁止）に**物理分離**して注入。→ 反捏造を保ったまま"未来を語るコピー"が書けるようになる。
- **オーサリングUI（superadmin 関係編集・提供価値/実績編集）**：時制・状態のトグルと新関係型の選択肢を追加。
- **ペルソナ**：現状のままで可（顧客像は現在の観察でよい）。将来的に「顧客の"なりたい姿"」を足す余地はあるが今回のスコープ外。

**移行の順序（dual-run 厳守・過去の理念オントロジー移行と同じ作法）**
1. カラム追加（既定値で全既存データ＝`current`/`proven`＝見た目も挙動も不変）。
2. 整合性チェックを時制対応にアップデート（`target`が無い間は従来と同じ結果）。
3. superadmin UI に時制・新関係型を出す（任意入力）。
4. 1社（テックブリッジ or ID INC.）で「目標の約束＋earnedByの計画」を試験投入し、整合性・コピーの before/after を確認。
5. 問題なければ本番反映。

## 7. ゼロベース再設計案（現状に引っ張られない・ただし反捏造は保持）

既存構造を前提にせず、「ブランドオントロジーとは何か」から引き直すとこうなる。

**中心概念を「ブランドの旅（Brand Journey）」に置く。**
ブランドを静的な"今の自己紹介"ではなく、**現在地 → 目的地 への道のり**として表現する。

- **3つの状態面**
  - 現在地（Who we are now）＝ 証拠に裏づけられた今の実像
  - 目的地（Who we are becoming）＝ ビジョンを頂点にした理想像・目指すポジション
  - 道のり（How we get there）＝ ギャップ＋獲得すべき証拠・マイルストーン
- **すべての要素は時制を持つ**（現有／目標／移行中）。同じ「提供価値」でも"今できる約束"と"目指す約束"を区別できる。
- **関係は"構造"と"時間"の2系統**：構造系（今どう結ばれているか＝既存6種）＋時間系（目指す・到達で手に入る・中間地点＝新3種）。
- **絶対ルール（反捏造の核）**：`target`（目標）タグの要素は、外向けの断定表現・事実引用に使ってはならない。使えるのは"目指す／これから"の宣言としてのみ。**"目標"と"事実"の壁を、今の"FACT/INTENT分離"と同じ強度でコードに固定する。**
- **整合性の問いが変わる**：今は「約束に証拠はあるか（自己整合）」。未来設計では加えて **「理想は描けているか」「理想に至る道（獲得すべき証拠）は繋がっているか」「現在地と目的地のギャップは自覚されているか」** を問う。ブランドを"点検"から"推進"の道具に変える。

この案でも **proof_point は生き残る**（現有＝信頼性、獲得予定＝道標）。ゼロベースでも結論は「消さず二役」。

## 8. おすすめの進め方（経営判断）

- **まず 6 の「加算移行」で小さく始める**のが安全。既存の強み（反捏造・一貫性）を1ミリも壊さずに、未来の層（時制タグ＋earnedBy＋整合性チェックの賢分岐）を足せる。
- 大きな概念転換（7のゼロベース＝"ブランドの旅"を中心に据える）は、6で手応えを見てから**次フェーズの構想**として持つ。
- 最初の実験は **ID INC. 自社ブランド**が最適。目指す姿と、それを証明するために今後獲得すべき実績（earnedBy）を1本描き、コピー/整合性の before/after を見る。

**次アクション候補**
1. 6の加算マイグレーション設計（カラム3本＋関係型3つ）を具体化して指示書化。
2. 整合性チェックの時制分岐＋新チェックの実装指示。
3. ID INC. で"目標の約束＋獲得計画"を1本入れて before/after 検証。
