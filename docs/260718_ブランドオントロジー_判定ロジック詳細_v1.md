# ブランドオントロジー 判定ロジック詳細（achievement_rule × Proof Point 測定値）v1

**作成日:** 2026-07-18
**位置づけ:** C案詳細設計 v1 の §2・§6 のうち「達成判定」部分だけを再精緻化する。ここで `achievement_rule`（機械判定条件）と Proof Point の測定値構造を噛み合わせ、達成率 `frac` の算出を厳密化する。コード変更はしない。
**このドキュメントが上書きする箇所（C案詳細設計 v1 への差分）:**
- **Proof Point は測定値カラムを持つ**（v1では「無変更」としたが、測定値は"事実"の一部なので追加。事実限定の原則は不変）。
- Desired Evidence の `target_value` / `target_unit` **単独カラムは廃止**し、判定に必要な目標値・単位は `achievement_rule` の中に集約（判定の**単一の正**を rule に一本化）。
- `verification_method` は**人間用**（各実績が本物かをどう確かめるか）、`achievement_rule` は**機械用**（達成/未達を数値判定）と役割を明確に分離。

---

## 0. 設計判断（3つ）

1. **測定値は Proof Point に置く。** Desired Evidence（DE）は「基準」、Proof Point（PP）は「その基準を満たすかを測れる事実」。事実の数値はPP側の客観属性。DEは複数PPを集約して判定する。
2. **判定の単一の正は `achievement_rule`。** DEの目標値・単位・集計方法・比較演算子はすべて rule 内に持つ（カラムと二重管理しない）。
3. **達成状態は原則自動（rule×PP測定値から算出）。** 手動は `achievement_state_override`（理由必須）だけの例外。`verification_method` は自動判定を代替しない（人が各PPの真正性を確認するための記述）。

---

## 1. Proof Point の測定値構造（`proof_points` へ追加）

事実限定は維持。測定値は「その事実の客観的な数量」なので追加してよい。

| 追加カラム | 型 | 既定 | 説明 |
|---|---|---|---|
| `metric_value` | numeric | null | その実績の数量（例 +18、3、95.2）。定性実績は null |
| `metric_unit` | text | null | 単位（例 `pt` / `件` / `%` / `社`）。**DE側 rule.unit と突き合わせる鍵** |
| `metric_label` | text | null | 数量の意味（例「ブランドスコア改善幅」）。表示・監査用 |
| `measured_at` | date | null | 測定/発生日（`created_at` とは別。`latest` 集計・鮮度表示に使用） |

- 定性的な実績（数値の無い事例・エピソード）は `metric_value=null`。これは `count`/`boolean` ルールには効くが、`aggregate` ルールの集計対象からは外れる（§4-3）。
- PP自体は**どのDEにも属さない独立した事実**。DEとの結び付きは関係 `verifies`（proof_point → desired_evidence）で表す。1つのPPが複数DEを `verifies` してよい。

---

## 2. `achievement_rule` スキーマ（`desired_evidence.achievement_rule` jsonb）

先頭に `version` を持つ前方互換 jsonb。`type` で分岐。

### 2-1. boolean（存在すれば達成）
```json
{ "version": 1, "type": "boolean" }
```
「立証する実績が1件でもあれば met」。定性目標向け（例「創業ストーリーを言語化した」）。

### 2-2. count（件数の閾値）
```json
{ "version": 1, "type": "count", "threshold": 3,
  "proof_filter": { "unit": "pt", "op": ">=", "value": 10 } }
```
- `verifies` するPPの**件数**で判定。`proof_filter`（任意）を満たすPPだけ数える（例「+10pt以上の改善事例」だけを1件と数える）。
- `count_distinct_by`（任意・**B案拡張**）：同一対象の重複カウント防止。C案では未対応＝件数は素の verifies 数。運用で二重登録を避ける（整合性 info で重複疑いを促すに留める）。

### 2-3. aggregate（測定値の集計と比較）
```json
{ "version": 1, "type": "aggregate",
  "agg": "sum", "unit": "pt", "op": ">=", "target": 45, "baseline": 0 }
```
- `agg`：`sum` / `avg` / `max` / `min` / `latest`（latest は `measured_at` 最新のPP値）。
- `unit`：**この単位に一致するPPだけを集計**（単位安全・§4-3）。
- `op`：`>=` / `>` / `<=` / `<`。met 判定に使用。
- `target`：目標値。`baseline`（任意）：部分達成率の起点（既定は §4-4 参照）。

### 2-4. manual（自動判定しない）
```json
{ "version": 1, "type": "manual" }
```
- 機械判定を放棄し、`achievement_state_override`（レビュー）だけで met にする。数値化できない戦略的達成向け。override が無ければ常に unmet。

### 2-5. 未設定・不正
`achievement_rule` が空 `{}` または壊れている場合は **`manual` とみなす**（勝手に met にしない）＋整合性 info「判定条件が未設定＝手動レビュー要」（§5）。

---

## 3. 判定に使う入力の確定

DE d の判定に使う集合と値：
- `P(d)` = `verifies` 関係で d に紐づく **Proof Point 集合**（端点解決済みのみ。幽霊エッジは除外）。
- 各 PP は `{ metric_value, metric_unit, measured_at }` を持つ（null 可）。
- `rule = d.achievement_rule`。
- override = `d.achievement_state_override`（あれば最優先）。

---

## 4. 達成率 `frac(d)` 算出アルゴリズム（0〜1）

```
function frac(d):
  # 0) 手動上書き最優先（例外・レビュー記録あり）
  if d.achievement_state_override != null:
     return map(override) = { met:1.0, partially_met:0.5, unmet:0.0 }[override]   # source="manual"

  P = verifiesProofs(d)      # 端点解決済み
  r = d.achievement_rule (or manual if empty/invalid)

  switch r.type:
    "boolean":
        return (P is nonempty) ? 1.0 : 0.0

    "count":
        Pf = P filtered by r.proof_filter    # 単位一致 & op/value を満たすPPのみ（filter無ければ全件）
        n  = |Pf|
        return clamp(n / r.threshold, 0, 1)

    "aggregate":
        Pu = { p in P | p.metric_value != null AND p.metric_unit == r.unit }
        if Pu is empty:
            flag(d, "測定値のある実績が無く自動判定不可")   # → unmet 扱い
            return 0.0
        a = aggregate(Pu.metric_value, r.agg)     # sum/avg/max/min/latest(by measured_at)
        return fracFromOp(a, r.op, r.target, r.baseline)

    "manual":
        return 0.0     # override が無い限り unmet
```

### 4-1. 達成状態ラベル（frac → state）
```
state(d) = frac==1.0 ? "met"
         : frac>0     ? "partially_met"
         : "unmet"
```
（override 時は override 値をそのまま state に。source="manual" を併記。）

### 4-2. clamp / aggregate
- `clamp(x,0,1) = max(0, min(1, x))`
- `aggregate`：`sum`=総和、`avg`=平均、`max`/`min`=最大/最小、`latest`=`measured_at` が最も新しいPPの `metric_value`（同日は `created_at` で決定）。

### 4-3. 単位安全（重要）
`aggregate` では **`metric_unit == rule.unit` のPPだけ**を集計対象にする。単位不一致のPPは**集計から除外**し、整合性 info「単位不一致の実績が集計対象外（rule単位=◯◯／実績単位=△△）」を出す（§5）。→ pt と % を足すような誤集計を構造的に防ぐ。

### 4-4. `fracFromOp`（方向と部分達成）
```
fracFromOp(a, op, target, baseline):
  if op in (">=", ">"):            # 高いほど良い
     b = baseline ?? 0
     met = (op==">=") ? a>=target : a>target
     f = clamp((a - b) / (target - b), 0, 1)      # target==b はガード（0除算→met?1:0）
     return met ? 1.0 : f
  if op in ("<=", "<"):            # 低いほど良い（解約率など）
     b = baseline ?? (2*target)                   # 既定の起点＝目標の2倍（無ければ）
     met = (op=="<=") ? a<=target : a<target
     f = clamp((b - a) / (b - target), 0, 1)      # b<=target はガード
     return met ? 1.0 : f
```
- 「高いほど良い」例：`op=">=", target=45, baseline=0` → a=30 なら frac=0.67（partially_met）、a=50 なら met。
- 「低いほど良い」例：`op="<=", target=5(%) , baseline=10` → a=7 なら frac=(10-7)/(10-5)=0.6、a=5以下で met。
- `baseline` を入れると「どこから測った部分達成か」が意味を持つ（起点未指定の恣意性を減らす）。

## 5. 判定に関わる整合性チェック（info・自動修正なし）

| 名称 | 発火条件 | メッセージ意図 |
|---|---|---|
| 判定条件が未設定 | `achievement_rule` が空/不正（＝manual扱い） | 「自動判定できません。条件を設定するか、達成は手動レビューで」 |
| 単位不一致の実績 | aggregate で `metric_unit != rule.unit` のPPが `verifies` にある | 「単位が違う実績が集計対象外です（rule=◯◯/実績=△△）」 |
| 測定値なしで判定不能 | aggregate だが対象PPの `metric_value` が全て null | 「測定値のある実績がありません（手動レビュー要）」 |
| 立証方法の欠落 | `verification_method` も `achievement_rule` も無い | 「達成をどう確かめるかが未定義」 |
| 手動上書き中 | `achievement_state_override != null` | 「自動判定でなく手動確定です（理由: …／実施: …）」＝透明性表示 |
| 重複カウント疑い（弱） | count で同一 `metric_label`＋近い `measured_at` のPPが複数 | 「同じ実績を二重に数えている可能性」（C案は弱い注意のみ） |

いずれも info。ウィザード完了判定（current の裏づけ欠落＝warn）には影響しない。

## 6. 具体例（4パターン）

**例1: 件数（count）**
DE「+10pt以上のブランドスコア改善事例を3件」
- rule = `{type:"count", threshold:3, proof_filter:{unit:"pt", op:">=", value:10}}`
- PP: A(+18pt), B(+12pt), C(+6pt), D(定性・値なし)
- 対象 = A,B（+10以上）。C は filter 外、D は値なし。n=2 → frac=2/3≈0.67 → partially_met。

**例2: 集計・平均（aggregate/avg）**
DE「導入企業の平均ブランドスコア改善を+15pt以上」
- rule = `{type:"aggregate", agg:"avg", unit:"pt", op:">=", target:15, baseline:0}`
- PP: A(+18), B(+12), C(+21)（すべて pt）。avg=17 ≥15 → met（frac=1）。
- もし %単位のPPが混ざっていたら集計対象外＋単位不一致 info。

**例3: 存在（boolean）**
DE「創業者の想いを言語化したストーリーを保有」
- rule = `{type:"boolean"}`。言語化した事実PPが1件 → met。

**例4: 手動（manual）**
DE「業界内で"AI×ブランディングの第一想起"を獲得」（数値化困難）
- rule = `{type:"manual"}`。override で met にする際は理由（例「主要媒体3件のインタビューで第一想起として言及」＋根拠PP）を記録。それまで unmet。

## 7. §6（実証進捗）との接続

各 DE の `frac(d)` を、C案詳細設計 §6 の重み付き式にそのまま投入：
```
実証進捗(vision) = Σ_d ( importance_weight_d × frac(d) ) / Σ_d ( importance_weight_d )
     （d は当該 vision が requires する DE。execution_state='cancelled' は分母から除外）
```
`frac` が rule×測定値から厳密に出るようになったので、進捗は「重み付き・単位安全・部分達成込み」で意味のある数値になる。**すべて動的算出・非保存**は不変。

## 8. C案詳細設計 v1 への反映差分（まとめ）

| 対象 | v1 の記述 | 本ドキュメントでの確定 |
|---|---|---|
| `proof_points` | 無変更 | **測定値4カラム追加**（metric_value/unit/label/measured_at）。事実限定は不変 |
| `desired_evidence.target_value/target_unit` | 任意カラムで保持 | **廃止**。目標値・単位は `achievement_rule` に集約（単一の正） |
| `achievement_rule` | 3型（count/value/boolean） | **4型に確定**（boolean / count / aggregate / manual）＋ version ＋ 単位安全 ＋ baseline ＋ proof_filter |
| 達成率 | 「min(1, 実測/target)」と概略 | **fracアルゴリズム確定**（型別・方向別・部分達成・単位安全・例外） |
| verification_method | 併記 | **人間用**（真正性確認）と再定義。機械判定は achievement_rule 専任 |
